# 评估体系（三层评估与金丝雀任务集）

> 用途：**模型升级 / 更换宿主工具 / 大改规则资产（AGENTS.md、模板、门禁脚本）之前**，先跑金丝雀任务集，验证体系性能未漂移再放量；以及月度体系级复盘。体系由概率组件（LLM）+ 规则资产 + 执行环境构成，任何组件更换都会让性能漂移，且漂移是**静默的**——不会有报错，只有"最近好像老被打回"的体感。评估体系让漂移从体感变成数字。

## 三层评估总览

| 层级 | 节奏 | 防什么坑 | 核心动作 |
|---|---|---|---|
| 资产级 | 改一处测一处 | 好心改坏（规则/模板/脚本的修改引入退化） | 修改后跑回归集 |
| 任务级 | 体系组件变更时 | 升级翻车（换模型/换宿主后通过率骤降） | 跑金丝雀任务集 |
| 体系级 | 月度 | 温水煮青蛙（指标缓慢恶化无感知） | 指标看板复盘 |

## ① 资产级（离线）

- 规则文件、提示模板、门禁脚本的每次修改，重放**历史已验证场景**：确认新能力生效、旧行为未退化
- 典型实体：jjspec 的 boundary-check 回归测试（六场景）——脚本修特殊文件名误拒后重跑，验证新能力（引号路径放行）与旧能力（中文路径/重命名拦截）同时成立
- 纪律：**上下文资产当代码管理**——AGENTS.md、提示、脚本走 PR/commit + 评审，有版本历史可回滚；它们是会被改坏的运行部件
- 没有回归集时，每次"修复"都是在赌没改坏别的——先攒回归集，再改资产

## ② 任务级：金丝雀任务集（Canary Suite）

**选集**：10~20 个基准任务，必须包含：

- 覆盖典型场景（各风险等级、各模块类型）
- **至少 5 个 AI 曾失败过的任务**——它们是最贵的测试用例（每个都是真实漏洞的复制品）；只测 happy path = 矿工带假鸟下井
- **冷启动例外**：新项目没有历史失败案例时，允许用**构造的失败场景**启动，但必须在"来源"字段显式标注 `⚠️ 构造`（与 `⚠️ 历史失败` 区分）；随真实失败积累逐步替换，目标仍是 ≥5 个真实来源——构造场景能测机制，测不出真实分布

**单个金丝雀任务的字段**：

| 字段 | 内容 |
|---|---|
| 任务输入 | Spec（含 AC）+ 重现/上下文 |
| 期望产出 | diff + 测试（或指定产物） |
| 通过判定 | AC 逐条对照，不是"看起来对了" |
| 来源 | 历史成功 / ⚠️ 历史失败 |
| 度量记录 | 首次跑完时填 |

**触发时机（三类，任一发生先跑金丝雀再放量）**：

1. **换模型**：同一宿主内切换底层 LLM——不同模型对规则遵循度、工具调用格式、错误自纠能力不同
2. **换宿主**：切换 AI 编码工具——宿主决定工具集形态与权限边界，流程依赖的能力（跑测试/读 diff）可能变化
3. **大改规则资产**：AGENTS.md 大改、模板升级、门禁脚本重写

**度量四件套**（每个任务记录）：

| 度量 | 含义 | 信号 |
|---|---|---|
| 一次通过率 | 首跑即过的任务 ÷ **全部已分配任务**（未完成的按未通过计） | 体系对任务的适配度 |
| 平均自纠轮次 | 通过前平均几轮"改→测" | 5 轮才过 = 反馈信号质量差 |
| token 成本 | 每任务消耗 | 突增 = 流程退化或模型变化 |
| 越界次数 | 触发边界拦截的次数 | >0 = 边界声明或执行有问题 |

对比基线：换组件前后的四件套对比，一次通过率跌 >10 个百分点或自纠轮次翻倍 → 先归因再放量。

**运行记录（每次跑金丝雀必填，否则前后差异无法归因）**：

| 记录项 | 内容 | 为什么必填 |
|---|---|---|
| 代码版本 | 被测仓库 commit SHA | 代码变了，指标变化可能来自代码而非体系 |
| 宿主与模型 | 宿主工具版本 + 模型标识（含版本号） | 换组件评估的核心自变量 |
| 规则资产版本 | AGENTS.md / 模板 / 门禁脚本 commit SHA | 规则改了等于体系改了 |
| 执行预算 | 每任务步数上限 / 轮次上限 / 超时 | 预算放宽会虚假提升通过率 |
| 失败任务统计 | 未完成任务**按未通过计入通过率分母**，同时单列"未完成数/完成率"；平均自纠轮次只统计完成且通过的任务，但**必须与未完成数一并报告** | 把跑不完的任务排除在分母外 = 用筛选美化指标；只报均值不报未完成数同理 |

> 归因纪律：上述任一项变化，本次结果不可与历史基线直接对比——先固定变量重跑，再谈漂移。

**载体定义（项目内合法落点，勿自由发挥）**：

- 任务集与运行记录是**项目数据资产**（失败历史 + 基线数据，只能归项目），固定落点：`docs/canary/suite.md`（任务集）+ `docs/canary/runs/<YYYY-MM-DD>-<触发原因>.md`（运行记录归档）
- 项目文档**只写数据**：任务表（字段见上）、运行记录（必填项见上）、现状与缺口；**机制定义（度量四件套/判定阈值/选集纪律）引用本 skill，不复制**——skill 升级改阈值后，项目里的复制品会变成过时规则
- 新建文件前的自检：删掉这个文件，损失的是**项目数据**（合法容器）还是只是**机制说明的复制品**（非法）？

## ③ 体系级（月度看板）

| 指标 | 算法（分子/分母） | 警戒线 |
|---|---|---|
| 门禁逃逸率 | 见下方演算 | >15% 需补门禁 |
| 人审打回率 | 人审打回 PR 数 ÷ AI 提交 PR 总数 | 突增 = 某层退化 |
| 变更失败率 | 引发回滚/事故的部署数 ÷ 部署总数 | 沿用 DORA，看 AI 是否恶化 |
| 交付周期 | 已获开工授权后首次进入执行段的 `started_at` → 上线时刻（包含等待方案批准的时间） | 北极星指标；按直通/走门、需求/缺陷分组 |
| 人机时间比 | 检查点上人的耗时 ÷ 任务总时长 | 自主性是否真实提升 |
| 回流率 | 每月教训回流条数（进 AGENTS.md/ADR） | 趋零 = 飞轮停转 |

交付周期起点记在 PRD 的续接区，免 PRD 的缺陷记在修复 Spec；仅文档任务不计入上线交付周期。续接/返工不重置起点，未上线项报告已耗时，不当作完成样本；历史“Spec 批准→上线”口径不能直接混算。

**门禁逃逸率演算**：

- 定义：**逃逸率 = 门禁后发现的问题数 ÷ 全部问题数**；全部问题 = 门禁拦截的 + 门禁后发现的（去重后的问题集合），门禁后发现 = 人审发现的 + 线上暴露的
- 示例（三个发现阶段分开列，不要混计）：**门禁拦截 3 个** + **人审发现 9 个** + **线上暴露 1 个** → 门禁后发现 = 9+1 = 10，全部问题 = 3+9+1 = 13 → 10÷13 ≈ **77%**——门禁基本是摆设，每 10 个问题 7.7 个靠人肉兜底
- **语义类问题须单独标注**：本就机器检查不了的问题（架构取舍、业务语义、命名品味）计入分母但不计入"应补门禁"的归因基数——否则一个合理依赖人审的项目会被"77% 必须补门禁"错误评价
- 修复动作：把逃逸问题逐个归因——**没有对应门禁**（补规则）/ **门禁太弱**（提醒改成阻断）/ **本就检查不了**（语义问题，人审职责）——三类去向不同，不是一股脑"加强门禁"

## 度量反模式（三条红线）

1. ❌ 只看"AI 生成代码占比"——vanity metric：占比只说明写得多；占比高 + 逃逸率高 = 漏得多
2. ❌ 拿 AI 和人比编码速度——维度错误：比整条交付流的周期与质量（含 review、返工、上线）
3. ❌ 金丝雀集只测 happy path——失败过的任务必须收录
