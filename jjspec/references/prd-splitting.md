# PRD 分册规范（大需求 / 多模块需求）

> 用途：新增大需求的**起稿规范**，以及存量单文件 PRD 的**迁移拆分规范**。
> 下游不变：本规范只约束需求层（prd）的组织方式；Spec、HLD、任务卡、门禁、归档仍按既有宪法与模板执行。
> 定位：jjspec 指令表分册类指令的执行细则（触发词清单以 SKILL.md 指令表为唯一正源）。

## 〇、触发规则

**仅由用户显式指令触发**，触发词清单以 jjspec SKILL.md 指令表为唯一正源（分册类指令），不做任何自动判定：命中即按本规范以分册方式组织需求文档——无论该需求覆盖一个模块还是多个模块、体量大小，均以用户指令为准。未触发时按既有单文件流程走；用户在单文件流程中途要求改为分册的，随时可切换。

## 一、结构约定（13 条规则）

**R1 双层同构**：`changes/<需求ID>/` 下为 `prd.md`（主）+ `prd-<两位序号>-<英文短名>.md`（模块，如 `prd-01-admin-auth.md`）。命名与落点遵守 `prd-constitution.md` 第八节（分册模块文件属带编号实体文件显式例外），本规范不另立命名规则。spec 保持单文件 `spec.md`、hld 保持单文件 `hld.md`，不分册。

**R2 主 PRD 独占全局章节**：背景与问题、目标与非目标（O-xx 全量）、用户与角色总表、AI 质量与评估、依赖与风险、非功能需求（REQ-NFR-xxx 全量含验收场景）、附 A 术语表 / 附 B 假设清单 / 附 C 约束清单 / 附 D 待澄清问题；携带 UI 原型时另加全局视觉验收约定块（`prd-constitution.md` 第九节）——主 PRD 是这些内容的**唯一事实源**。同一内容禁止在模块文件中出现第二份。

**R3 模块文件自包含**：每个模块文件是完整 PRD 结构（frontmatter、版本表、变更续接、1~8 章、附 A~D），单独加载即可开工。全局项一律写「见 `prd.md` 第 X 章」式 ID 引用；附录只放与本模块相关的条目索引（编号 + 主题摘要 + 指针），不复制全文。宪法认可的轻量形态对模块文件同样适用：单卡且不触线的模块可按轻量必填项省略章节，`本章无内容：<原因>` 规则不变。

**R4 主 PRD 第 4 章 = 索引**：每模块一节 = 模块范围一句话 + REQ-ID/名称/优先级清单表 + 相对链接 + **显式加载指令**（明确写"实现或评审本模块前，须加载同目录 `<文件名>`"）。AI 不会自动跟随 Markdown 链接，加载必须是显式指令。

**R5 主 PRD 顶部必须有「文档结构与加载约定」表**：什么时机只读主 PRD、什么时机加读哪个模块文件、改模块内容改哪里、改全局内容改哪里。并声明 REQ 总数守恒。

**R6 编号保号**：REQ-xxx / UC-xxx / O-xx / A-xx / C-xx / Q-xx / NFR 编号迁移与起稿全程不变，作废不复用。原稿存在编号缺陷（重号、错序）时不得擅自改号——登记到变更续接，经用户确认后重编号，并在基线附录留**新旧映射说明**。

**R7 零改写迁移**（存量迁移入口适用）：需求正文（EARS 描述、Scenario、表格、附录行）用编辑器级复制等机械方式搬运（暂无专用迁移脚本），禁止凭记忆复述；AI 只撰写骨架（背景、目标引用、索引句、加载约定）。骨架中引用原文事实时逐条对照原文。

**R8 计数守恒**：主 PRD 第 4 章索引的 REQ 数 = 各模块 4.2 详述条数之和；Scenario 总数迁移前后一致；附 D 待澄清条目数一致。

**R9 验收汇总归位**：各模块文件第 8 章放本模块 REQ-ID ↔ 验收标准 ↔ 验证方式映射；主 PRD 第 8 章只做指向索引（模块 → 文件 → 条数）。

**R10 失败路径归位**：原文有独立失败路径表的，原样迁入模块文件 3.4；没有的，从该模块 Scenario 生成「失败场景索引」（场景名 → REQ-ID），并显式声明断言以 4.2 对应 Scenario 为准。

**R11 缺陷显式登记**：迁移/起稿中发现的原稿问题（重号、矛盾、悬空引用、[NEEDS CLARIFICATION]）一律登记到主 PRD 变更续接，不得静默修复或静默丢弃。

**R12 元信息处置**：原稿版本表沿革在主 PRD 版本表加"来源沿革"行注明去向；原「变更续接」按新结构重写（保留授权范围、未决项）；被索引取代的导航句可弃（属导航非需求）。

**R13 UI 真源加列**：需求携带 UI 视觉输入（HTML 原型或设计稿）时，全局视觉验收约定块归主 PRD（并入 R2 清单）；全部模块文件第 8 章验收映射表同步加「UI 真源」列，列格式、空页面、前置产物四件套与分支验收规则见 `prd-constitution.md` 第九节。存量迁移时，入口 B 三重校验追加一项：全部模块文件加列完成，且每条非「—」锚点可定位到原型页面或设计稿消化产物页面。

## 二、两条入口路径

### 入口 A：分册起稿（新需求）

1. 指令触发后，与用户对齐模块清单与文件命名（哪怕只有两个模块，用户要求分册即分册）
2. 直接按结构 R1~R5 起草主 PRD 与各模块文件；需求打磨（EARS、非目标、失败场景）照常按宪法执行，只是落点分散到各模块文件
3. 后续每轮澄清/修订直接写进对应模块文件，主 PRD 只同步索引行（R5 的约定表已写明改哪侧）
4. 附 D 的 Q-xx 集中在主 PRD（全局唯一事实源），模块文件只放相关编号索引

### 入口 B：存量迁移（单文件补救拆分）

1. **结构扫描**：只读标题层级，输出「模块章 / 共享章 / 跨模块章 / 附录」清单；与用户确认模块切分与命名
2. **迁移映射表**：每个 REQ / UC / O / A / C / Q / 独立表格 → 原文行号 → 目标文件章节；此表是不遗漏的核对基线
3. **骨架编写**（AI 写）：主 PRD 全局章节 + 各模块 1/2/3/5/6/7 章
4. **机械搬运**（编辑器级复制，暂无专用脚本）：4.1 总览表、4.2 需求详述（含标题层级整体下移）、第 8 章验收表、附 A~D 全文
5. **三重校验**（AI 自行执行并随交付输出结果，全绿才算完成；不要求用户逐项核对）：
   - REQ 深度比对：每条 REQ 的标题、描述行、全部 Scenario 逐字符一致（层级差除外）
   - 行级覆盖：原文全部非空正文行在产物中可找到（未命中仅允许元信息/导航，逐行列出并说明）
   - 格式检查：frontmatter 六字段、章节骨架完整、EARS 句式、Scenario 含 GIVEN/WHEN/THEN、P0 占比与超线理由
6. **登记**：变更续接写明授权范围、发现的缺陷、下一步；停在定稿前等待用户指令

## 三、与既有体系的衔接（不改变任何现有机制）

| 环节 | 衔接方式 |
|---|---|
| 定稿 | 仍只能由用户指令触发；建议逐模块或整批定稿，主 PRD 与模块文件同批登记版本 |
| 拆 Spec | 单文件 `spec.md`：每条 REQ 的 Scenario 原样转 AC，按 REQ-ID 分节；来源在 Spec frontmatter `source_requirement` 注明主 `prd.md` 路径及版本与涉及模块文件 |
| 拆 HLD | 单文件 `hld.md`：架构决策是全局的，不分册；改动面按模块引用 |
| 任务卡 DAG | 不变：默认单卡单模块，跨模块原子变更注明理由 |
| 门禁 | 不变：分册本身不改变触线判定；鉴权、金额、跨模块等照常走门 |
| 归档 | 不变：`git mv changes/<需求ID>/ changes/archive/<日期>-<需求ID>/` 整目录迁移，模块文件自动随归；主 PRD 与模块文件同目录，**相对链接天然不断**，归档分册仍自洽可导航 |
| 回流基线 | 不变：仅目标/非目标/角色/成功标准触碰时修订 `docs/PRD.md` 对应章节 + 版本表登记；**模块行为规格永不复制回基线**；基线不挂任何分册指针（归档快照不可变，指向它当"现状"会产生多快照歧义） |
| 后续变更 | 归档分册是**不可变快照，永不改写**；后续需求修改某模块行为时，新开 `changes/<新需求ID>/` 分册，其模块文件承载**变更后的完整行为规格**（自上一版分册机械迁移 + 修订，编号保号、修订走版本表）；旧归档不动 |
| 查当前行为 | 某能力的当前行为规格 = 经 `changes/INDEX.md` 编年**倒查最近一次涉及该能力的归档分册**（最近一次变更非分册时，行为真相为该归档目录内的 `spec.md`/`prd.md`，并以代码与测试实况复核）；分册入口只存在于 INDEX（每变更一行），基线 PRD 只回答能力边界，不回答行为细节 |
| 能力编年 | `changes/INDEX.md` 一行一变更，入口指向该次归档分册目录 |

三层职责速记：`docs/PRD.md` = 能力边界快照（低频，触碰才修订）；`changes/INDEX.md` = 能力编年（逐变更，分册唯一入口）；`changes/archive/` = 不可变行为快照（最新一份 = 当前行为真相）。

> **校验归属**：第二节入口 B 第 5 步的三重校验及 R1~R12 的符合性检查，全部由 AI 在交付前自行执行，校验结果随交付一并列出（含未命中行清单与计数对账），属交付物的一部分；用户只做定稿决策，不承担校验义务。当前无配套执法脚本，校验为 AI 手工逐项执行，须输出原始对账清单（逐行命中/未命中明细与计数），禁止只报结论；后续补脚本时升级为「脚本执法 + AI 抽核」。
