# 任务卡模板 + DAG 拆卡法

> 用途：任务卡 DAG 拆解阶段、编码执行前。直通模式以有效定稿 PRD 和 draft Spec/HLD 拆卡；走门模式须当前 Spec/HLD 已获用户批准。仅恢复既有行为的缺陷可免 PRD，以有预期依据的修复 Spec 拆卡，模式按 `prd-constitution.md` 风险复判规则确定。**单卡 = 单窗口**（卡体量以 agent 单窗口上下文可完成为判据）；**默认单卡单模块**（跨模块原子变更须注明理由）；单卡变更 100~400 行为宜。
> 落点：**一张卡一个文件**——`changes/<需求ID>/tasks/TASK-<编号>.md`（编号与卡 id 一致）。禁止多卡并进单文件：CI 按卡文件路径做在场卡过滤与边界归属，混放会让过滤与越界判定失效。

## 单卡模板

**节标题纪律**：卡内 `##` 节标题 = 机器解析锚点（task-done-gate.sh 按整行精确匹配提节）+ 下游窗口章节自查锚点——**裸标题固定节名，禁止括号后缀与注释性改写**（`## 契约（必接端点清单 = 硬约束…）` 类变体会让节提取静默为空，done 门禁误报节缺失，下游窗口也认不出合法章节）；适用前提与说明一律写进节内引导注释首行，不进标题行。合法节名 = 本模板列出的节（通用节 + 页面卡附加节）；项目确需新增节时允许，同样裸标题、前提写节内注释。

```markdown
---
id: TASK-04
title: 定金支付流程
risk: high | medium | low        # high = 预计产出红线赌注（判据见拆卡规则 5）→AL1 逐卡执行；低→AL2 自主循环
depends_on: [TASK-01, TASK-02]   # DAG 依赖，指向被依赖者
spec: changes/<需求ID>/spec.md   # 本卡对应哪份 Spec（spec_ac 的归属，防多 Spec 的 AC 编号歧义）
spec_ac: [AC1, AC4]              # 本卡验收对应上述 Spec 的哪些 AC
ui_source_page: ui-specs/<产品ID>-<业务大项>/pages/p-<序号>-<短名>.md   # 页面卡必填：本卡还原的页面规格文件（目录名同宪法第九节第 10 条）；非页面卡省略此行
date: YYYY-MM-DD
status: pending | in_progress | blocked | done   # done 语义（机械校验：assets/task-done-gate.sh）= ## 验收 逐条带证据 + risk: high 卡风险报告条目（红线条目或消解行）在场 + 页面卡 ui-gate 已执行，禁止缺证置 done；done 非终态——报告赌注被质疑时拉回 in_progress 修复（处置正源 = 风险报告节）
---

## 拆卡规则

1. **默认一张卡单模块内可完成**——跨两模块默认拆两卡（AI 原稿爱合成大卡，人工必拆）。例外：接口与其调用方必须原子变更时可同卡，须注明理由，仍守单卡 = 单窗口（单窗口可完成）
2. **依赖必须显式成 DAG**：有向（指向被依赖者）、**无环**（T04 等 T05、T05 又等 T04 = 拆错了重拆）。**DAG 完备性硬门（第一张卡开工前须过 `assets/task-dag-check.sh`，fail-closed）**：① AC 反向完备——spec 的每条 AC 至少被一张卡的 `spec_ac` 认领，无卡认领 = DAG 未闭合，禁止开工，**禁止以「后续窗口补拆」为由滚动开工**（实战教训：20 分册 PRD 只拆 7 卡即开工——上下文压力下拆卡产出被自适应裁剪，描述性「先拆全卡」约束不住，必须机械执法）；② 依赖闭合——`depends_on` 不引用不存在的卡、无环无自依赖；③ 卡 `spec` 字段指向同一正主 spec（防多 Spec 的 AC 编号歧义）。门禁对象是「开工而 DAG 未闭合」：未建 tasks/ 的需求未到拆卡阶段不拦；无 spec.md 的纯缺陷修复需求只查 ②③
3. **执行调度判据**：拓扑排序 = 兜底执行顺序——`depends_on` 边是硬串行约束，**下游解堵统一 = 前置卡 done（task-done-gate 全绿）**：下游同工作区直接开工，连续执行不等提交，不按风险分级——卡级同步人审已废止（v1.21.0），前置卡的风险赌注走风险报告异步受理（拆卡规则 5）；赌注被质疑打回前置卡时，按条目「若赌错」声明的返工面重修下游（事后返工替代事前阻塞）。**「合入」与解堵脱钩**：合入 = 改动进入共同开发分支的纯 Git 动作（PR 制项目 = 分支 PR merge；本地单干项目 = 按卡 boundary 分批 commit），由用户在提交窗口按拓扑序批量触发——AI 不得以「未提交/未合入」为由阻塞下游开工或静默挂起（实战教训：前置卡测试全绿后以「等待基线合入」挂起全链——下游开工不需要 commit，工作区改动即生效，合入只是提交窗口的批量动作）。**无依赖分支 ≥ 2 时，拆卡交付须附带调度方案由用户选择，禁止默认静默串行**（交付时机 = 拆卡完成停靠，见 SKILL.md ⑥行——停靠时单分支报拓扑序与首个业务闭环（即要素④）、多分支交四要素方案；用户的「继续」即对所报调度方案的放行）——并行方案四要素：① 并行分组（同组卡互不依赖）；② 每组窗口数（每窗口严格单卡，守单卡 = 单窗口）；③ 合并顺序（按拓扑序逐组合入；共同修改同一文件的卡归入同组串行，防合并冲突）；④ 首个业务闭环（适用前提：≥2 卡的任务图，单卡天然闭环不适用）——报出用户可感知的端到端操作路径（入口→持久化/呈现）由哪些卡构成、位于拓扑序何处、其全部传递前置卡数，不在拓扑序最前时须给出理由；必要权限、数据约束、兼容迁移可计入前置，但须逐项说明该项确实挡住此路径，与该路径无关的模块卡不得计入；该要素只显影与排序，不是减卡依据，不解除 DAG 完备性硬门。用户选串行或环境不支持多会话 → 按拓扑序逐卡执行。**调度方案须标注 risk: high 卡位置**（其赌注条目为风险报告红线候选，供用户审读定位）。**拆卡拓扑设计**：被 ≥2 张消费卡依赖的前置位卡优先设计为低风险纯定义/配置卡（高风险实现后置叶子化），缩小赌注质疑打回时的返工面；**业务切片优先（即调度方案要素④之首个业务闭环）**——拓扑序最先开工的卡集合应构成一条最小端到端业务切片（用户可感知操作从入口到持久化/呈现），技术层卡（库表/接口/装配/发布工具）除非挡住该切片路径，不得排在其前；本判据只约束拓扑优先级，禁止据此减卡或「先做切片、其余后补」（DAG 完备性硬门照常）
4. **单源资产先拆卡、消费方 depends_on 指向它**——本次需求中被 ≥2 张消费卡共享的底层资产（单源四件套：domain 领域模型、tokens 样式变量、OpenAPI 契约、Adapter 端能力接口，及共享包）各自独立成卡，拓扑序先行；消费方卡 `depends_on` 指向对应单源资产卡；**禁止把单源资产的定义/增改混进第一张消费卡**（单源与消费同卡会让后续消费方卡随手改契约，边界门禁与单源纪律在执行层失效）。互不依赖的多张单源资产卡可并行
5. **赌注申报与异常停泊（v1.21.0 起替代卡级同步人审——人只受理赌注，不逐卡审实现）**：
   - **赌注判据（充要三条件，逐条过，缺一即非赌注）**：赌注 = 实现所依赖的可证伪假设，且同时满足——①**外部性**：描述实现边界之外的现存世界状态（客户存量数据/真实用户行为/生产环境/第三方系统/时间推移的外部变化），不是代码内部事实、不是未来可能的需求、不是设计审思；②**不可核实性**：读代码、跑测试、查 spec 三步内能定 = 已验证事实/规格承诺，禁入；**判「不可核实」前必须先走三步核实并留痕（字段格式见「风险报告」节条目模板），任一步走通（找到担保）= 判据②已破 → 消解行，不是预期条目——禁止以「未核实」冒充「不可核实」**；③**对账点在场**：能指名赌错暴露的具体位置（谁在哪次真实世界操作中发现）。**反类禁入**：「后续不出现 X」类未来扩展性假设、工程信心（「可稳定实现」）、实现时即定的技术事实（要不要迁移）、代码审查可核实的内部事实、测试缺口（赌错时 CI 先红 = 补测试，不是消赌注）。发现即写入 `changes/<需求ID>/risk-report.md`（条目格式与消费机制见「风险报告」节），写入义务跟赌注走、与卡级无关
   - **红线判据**：赌错后系统照常运转（测试绿、功能可用、无外部信号），只与真实世界对账时才暴露（真付款/真并发/真攻击者/真数据规模）= 红线赌注。**`risk: high` = 拆卡时预计产出红线赌注**；done 时红线条目必须在场，预测落空（实现中发现该假设已有担保）写消解行「预期赌注『X』消解——担保来源:<spec ACx/测试文件>」；拆卡标 low/medium 的卡实现中发现红线赌注 → 置 high 并在「## 卡内修订」说明（风险级别由赌注实际产出验证，不从域命中猜）。机械执法 = `assets/task-done-gate.sh`（risk: high done 时报告条目或消解行在场）
   - **异常停泊（唯一卡级同步停靠）**：修复路径必须触及上游工件（PRD/Spec/HLD 的 AC、非目标、契约等）才能继续 → 停，升级人决策（需求或设计错了或有遗漏）；修复落在本卡边界内（改代码、改测试）→ 自主修，禁止停泊（实战教训：发现矛盾静默绕过——PRD 永久排除的菜单被实现 AI 自造挂上存活三轮）
   - risk: high 卡禁止 AL2 自主执行（AL1 逐卡，gates.md 分级）；先标 done 后补条目的时间窗 = 虚假状态；AI 不得以"自查无赌注/无矛盾"替代报告条目申报（验收证据与赌注申报同为 AI 自产，自证无效——报告条目是赌注的唯一登记位）。申报时确认零真赌注（拆卡预测落空）→ 消解行是唯一合法收口（格式同上行消解行，担保来源写三步核实中哪一步 + 卡级降级）；为满足条目在场而硬造伪条目 = 虚假状态，与先标 done 后补证据同罪
   - 旧「人审请示材料包五件」废止（v1.21.0）：AC 对照、diff 清单回归「## 验收」与 PR 证据正源；变异存活率随发布证据包展示（gates.md 发布证据包节）；「监督策略焦点自查」并入赌注申报过程。机械验证覆盖不了的问题（断言语义真伪、竞态/金额精度、越界与安全）仍归人审三焦点（gates.md），消费位 = 抽审与赌注审读
6. 每张卡自带测试要求——行为变更卡（边界覆盖行为文件）必须在 `## 测试文件清单` 声明看护测试文件，"AC↔测试对应性"门禁（`assets/ac-coverage-check.sh`）强制：清单条目存在且为测试文件、`spec_ac` 不含幻觉引用。断言语义是否真对应 AC 归人审三焦点（防"只断言状态变了"的弱断言）。**测试文件清单的任何变更（新增/移位/聚合/改名）必须同步修正「## 边界」boundary，保证测试文件位于卡边界内（boundary-check.sh 对边界外文件报越界），并在「## 卡内修订」节说明**。项目登记集成标记约定后（AGENTS.md integration-mark 块），**risk: high 行为卡的清单须含 ≥1 个集成标记测试条目**（ac-coverage-check --integration-mark 强制；集成测试骨架允许占位——断言先写、环境配置后补；禁 mock 主依赖为项目 R 规则红线，判据见 gates.md 第二层）
7. 仅写任务卡不授予编码权限；开始实现前核验已有开工授权。拆卡或实现中发现新增触线条件，记录在「## 卡内修订」节并转走门；Spec/HLD 修订影响本卡时置 `blocked`，同步后按当前模式核验适用批准，再继续。
8. **UI 需求的前置卡与页面卡开工门槛**：携带 UI 视觉输入的需求，四件套前置卡（设计规范 Token / 图标清单 / 页面布局规格 / 页面-REQ 映射，判据见 `prd-constitution.md` 第九节第 9 条）先于页面卡拓扑序交付，页面卡 `depends_on` 显式指向对应前置卡；前置产物未过机械校验前页面卡不得开工。页面卡实现只读消化规格（`ui-specs/`），不读原始视觉输入。**页面卡开工三门槛（缺一不得开工，结果登记执行进度 ui-gate）**：① 对应页面规格 frontmatter `digest: quantified`（逐项量化完成；清单级页先补消化，门槛可按页校验：`ui-pack-check.sh <目录> --require-digest p-<序号>`）；② 卡内 `## UI 规格摘录` 完成（**全量摘录 + 覆盖率 N/M 登记**，编码对照纪律见该节注释——厚规格必须对照开发，禁止摘要式摘录后自由发挥）；③ UI 四件套机械校验通过。**页面视觉验收逐卡内联**：页面卡实现完成即对该页执行视觉验收（HTML 路线 = 冻结原型重跑基准 + pixel-diff ≤ PRD 阈值；设计稿路线 = 结构化断言），超标即打回本卡（HTML 路线超标后的修复节奏与停止条件见 `ui-spec-guide` 第四节「HTML 路线 pixel-diff FAIL 修复闭环」——先归因后修改、逐轮差异率登记本卡执行进度、连续 2 轮无下降即停）；D0/CI 为全量复跑与收尾，**不得以 D0 终验替代逐卡内联**（终验发现偏差时返工面已扩大到全部页面）。注意与拆卡规则 4 的"单源四件套"（domain/tokens/OpenAPI/Adapter）是两个不同概念，互不替代——UI 消化产物由 UI 规范管线产出，非本次代码开发拆出。**验收铁律随卡流转**：页面卡派发子代理/新窗口执行时，调度 prompt 必须携带验收条款原文摘录（本条三门槛 + ui-gate 合法格式 + 逐卡内联验收），规范 → 卡 → prompt 逐级"原文在场"而非"精神在场"——禁止只传卡 ID 让下游凭记忆重建条款（实战教训：会话早期加载的规范到执行时已不在有效注意力，重建靠"记忆中的卡片形状"）
9. **页面卡的排除项与菜单对账前置**：在第 8 条三门槛之上另有两项——① 「## 排除项检查」节完成：本卡关联 PRD 册次非目标表逐条核对，命中永久排除/未解禁推迟项禁开工；② 卡触碰菜单/路由/侧栏结构（边界含路由注册表、菜单或导航组件，或增删页面）时「## 菜单/入口对账」节必附 `menu-recon-check.sh` 结果——菜单结构以 ui-specs 中 entry 含 menu 的页面清单为唯一正源（宪法第九节第 12 条），实现不得自造菜单项。文案覆盖率断言（ui-spec-guide 第三节第 7 条）结果记入执行进度 ui-gate 行
10. **观测采集落点完备性**——HLD「观测与灰度声明」节的观测指标表若存在，其声明的采集落点文件须被至少一张卡的「## 边界」认领（通常并入对应行为卡，或单拆埋点卡）；无卡认领 = 拆卡不完整，禁止开工。HLD 免填本节（直通单卡精简路径 / 本章无内容）时不适用本条

## 风险报告（`changes/<需求ID>/risk-report.md`）

> 卡级同步人审的替代物（v1.21.0）：赌注的唯一登记位与处置正源。随第一张产赌注的卡创建；格式正源本节。

条目格式（一赌注一条，数量不限；红线置顶；赌注行双硬性见下方说明）：

```markdown
### TASK-04 定金支付流程 ｜ 红线 ｜ 2026-11-14
- 赌注：定金在锁定期内金额不可变——假设不存在"锁定中改价"的并发路径（对账点：结算单与应收账款对账时发现尾款不符）
- 核实留痕：查 spec×（AC3 只约定锁定期金额不变，未约定并发改价路径）；跑测试×（现有并发用例不含改价分支）；读代码×（deposit 模块无互斥原语）——三步均未定 → 登记
- 若赌错：锁定期改价的订单尾款对不上账。返工面 = TASK-05、TASK-07 重做 + deposit 状态机重写；升级面 = spec AC4 需补"锁定期金额冻结"表述
- 回滚性：可回滚——改动收敛在 deposit 模块内，无 schema 变更（封闭三态：可回滚 / 部分可回滚（说明残留）/ 不可逆（必须说明为什么））
- 机器信号：并发原语（锁）新增 ｜ deposit_locked_amount 字段新增（形态标签如外部依赖/schema 变更/并发原语/安全面，供审核 agent 对账——diff 有依赖形态、报告无条目 = 未声明赌注，打回）
- 处置：待读
```

- 处置态封闭三值：**待读**（默认）/ **认可**（登记日期）/ **质疑**（登记日期 + 打回卡号，卡回 `in_progress` 修复后重走门禁）；处置正源 = 本文件条目，卡上不复制（防双源漂移）
- **赌注行双硬性**：① **人话**——写给不看代码的人审读，用业务语言说清「赌的是什么世界状态」；代码标识符、schema 细节、实现术语归「机器信号」行，假设必需的术语最多保留一个且随附白话解释（说不成人话的赌注多半是伪赌注）；② **对账点**——赌注行括注「（对账点：谁在哪次真实世界操作中发现）」，写不出对账点 = 不是赌注（伪赌注如「后续不出现第三变体」在此格式下自然无解）
- **核实留痕行**：预期条目必须在「- 赌注」行后紧跟「- 核实留痕」行，逐项记录三步核实各走了哪步、查了哪里、结论（步、落点、结论三要素齐）——任一步走通（找到担保）= 判据②已破，改写消解行「消解——担保来源:<spec ACx/测试/兜底实现>」，禁止以「未核实」冒充「不可核实」（判据正源 = 拆卡规则 5 赌注判据②）；仅「已核实」三字无落点 = 视同未留痕，按伪条目处置
- **落位四象限（登记前先落格；报告只收前两格；格与判据的推导正源 = 拆卡规则 5 赌注判据）**：

| 情形 | 落位 |
|---|---|
| 赌错后系统照常运转（测试绿、功能可用），只在真实世界对账时暴露——真付款/真并发/真攻击者/真数据规模 | 红线条目（risk: high 卡 done 必在场） |
| 赌错影响功能正确性且无现成担保，对账点可指名 | 普通条目（报告内，红线区外） |
| 疑似赌注但三步核实走通——担保在场（测试覆盖 / 本地兜底 / 契约已定义） | 消解行「消解——担保来源:…」，不写预期条目 |
| 无可证伪假设的既定事实——遗留工作项、已知限制、后续卡计划 | 卡内修订节，不进报告 |

  实战对照：后端 GET /audit 匹配口径未逐项实测、前端已有本地二次过滤兜底——担保在场 → 错落 = 写成预期赌注条目，正落 = 消解行「消解——担保来源：前端本地二次过滤」；「行展开未改为真实调用」= 无可证伪假设的遗留项 → 错落 = 占风险报告条目，正落 = 卡内修订「遗留：待接真实调用，留待后续卡」
- 红线判据与「无赌注不写行」原则见拆卡规则 5——低风险无赌注卡零义务，什么都不写；risk: high 卡 done 时条目在场（红线条目含「- 赌注:」且赌注行含对账点子句，或消解行含「消解——」）由 task-done-gate.sh 机械执法——机械只兜格式在场（对账点子句拦伪赌注填空），赌注真伪终审 = 提交时刻处置表态；核实留痕行的真伪机械暂不核验，归赌注审读对读（三步留痕给了审读者可逐项复核的落点，空泛留痕按伪条目打回）

消费时刻（三锚点，均不要求 agent 停等）：

1. **需求全部卡 done** → 随交付主动全量展示报告（摘要行：本需求 N 条、红线 M 条、未读 K 条 + 逐条赌注），纯展示不阻塞
2. **提交指令到达**（用户发起，人必然在场）→ 存在待读条目则挂起提交一次，逐条表态（认可/质疑）后放行；AI 代写处置留痕——读与不读的机械差别只在这一个闸口
3. **下一需求①预检** → 报未读条目数（长期不提交的兜底）

## 反例（来自实战）

- 38 个文件的"新模块 bootstrap"= 8~12 张卡，不是一张
- "实现切面 + 全量生效"应拆为：骨架卡（含生效范围控制/试点模块）→ 脱敏卡 → 输出通道卡 → 放量卡
- 高风险卡测试跑绿即标 done、风险报告无红线条目——赌注未申报即放行下游，赌错时返工面失控（v1.21.0 起条目缺失由 task-done-gate.sh 机械拦截）
- 用扩展性假设（「后续不出现 X」）、工程信心（「可稳定实现」）、代码可核实事实凑红线条目——赌注判据三充要条件逐条过，全不过 = 拆卡预测落空，走消解行降级，不是填空
- 「不确定但已脱手」事项写成预期赌注——兜底实现即担保来源，三步核实走通该走消解行；无可证伪假设的遗留工作项不进报告（实战：后端匹配口径已有本地二次过滤兜底仍登记预期赌注、「行展开未接真实调用」当赌注条目，报告信噪比被稀释）
- TASK-017"31 页挂载冒烟"先标 done 后补证据（时间窗内验收项为空），且补的测试只断言"组件可加载"，连逐页挂载都不算达标
- 验证证据填一行汇总（"mvn package 通过，N 测试全绿"）替代 ## 验收 逐条对照——done 语义被"我认为完成了"填平，批量 stamp 每卡 1 个动作完胜逐条验收的 3~5 个动作，速度偏好再次战胜纪律
