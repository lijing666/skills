# 任务卡模板 + DAG 拆卡法

> 用途：任务卡 DAG 拆解阶段、编码执行前。直通模式以有效定稿 PRD 和 draft Spec/HLD 拆卡；走门模式须当前 Spec/HLD 已获用户批准。仅恢复既有行为的缺陷可免 PRD，以有预期依据的修复 Spec 拆卡，模式按 `prd-constitution.md` 风险复判规则确定。**单卡 = 单窗口 = 单 PR；默认单卡单模块**（跨模块原子变更须注明理由）；单卡变更 100~400 行为宜。
> 落点：**一张卡一个文件**——`changes/<需求ID>/tasks/TASK-<编号>.md`（编号与卡 id 一致）。禁止多卡并进单文件：CI 按卡文件路径做在场卡过滤与边界归属，混放会让过滤与越界判定失效。

## 单卡模板

```markdown
---
id: TASK-04
title: 定金支付流程
risk: high | medium | low        # 高风险→AL1 逐卡+100%人审；低→AL2 自主循环
depends_on: [TASK-01, TASK-02]   # DAG 依赖，指向被依赖者
spec: changes/<需求ID>/spec.md   # 本卡对应哪份 Spec（spec_ac 的归属，防多 Spec 的 AC 编号歧义）
spec_ac: [AC1, AC4]              # 本卡验收对应上述 Spec 的哪些 AC
ui_source_page: ui-specs/<产品ID>-<业务大项>/pages/p-<序号>-<短名>.md   # 页面卡必填：本卡还原的页面规格文件（目录名同宪法第九节第 10 条）；非页面卡省略此行
date: YYYY-MM-DD
status: pending | in_progress | blocked | review | done   # done 语义（机械校验：assets/task-done-gate.sh）= ## 验收 逐条带证据 + 验收含人审项的已有人审记录 + 页面卡 ui-gate 已执行；验收含人审项未审时最高只能置 review（待人审），禁止自行置 done
---

## 拆卡规则

1. **默认一张卡单模块内可完成**——跨两模块默认拆两卡（AI 原稿爱合成大卡，人工必拆）。例外：接口与其调用方必须原子变更时可同卡，须注明理由，仍守单卡 = 单窗口 = 单 PR
2. **依赖必须显式成 DAG**：有向（指向被依赖者）、**无环**（T04 等 T05、T05 又等 T04 = 拆错了重拆）。**DAG 完备性硬门（第一张卡开工前须过 `assets/task-dag-check.sh`，fail-closed）**：① AC 反向完备——spec 的每条 AC 至少被一张卡的 `spec_ac` 认领，无卡认领 = DAG 未闭合，禁止开工，**禁止以「后续窗口补拆」为由滚动开工**（实战教训：20 分册 PRD 只拆 7 卡即开工——上下文压力下拆卡产出被自适应裁剪，描述性「先拆全卡」约束不住，必须机械执法）；② 依赖闭合——`depends_on` 不引用不存在的卡、无环无自依赖；③ 卡 `spec` 字段指向同一正主 spec（防多 Spec 的 AC 编号歧义）。门禁对象是「开工而 DAG 未闭合」：未建 tasks/ 的需求未到拆卡阶段不拦；无 spec.md 的纯缺陷修复需求只查 ②③
3. **执行调度判据**：拓扑排序 = 兜底执行顺序——`depends_on` 边是硬串行约束，**下游解堵条件按前置卡风险分级**：前置卡为低风险 → 其 done（task-done-gate 全绿）即解堵，下游同工作区直接开工，连续执行不等提交；前置卡为 `risk: high` → 其 review 经人审通过（执行进度登记批准人+时间）才解堵（人审可能打回，打回面必须受控）。**「合入」与解堵脱钩**：合入 = 改动进入共同开发分支的纯 Git 动作（PR 制项目 = 分支 PR merge；本地单干项目 = 按卡 boundary 分批 commit），由用户在提交窗口按拓扑序批量触发——AI 不得以「未提交/未合入」为由阻塞下游开工或静默挂起（实战教训：前置卡测试全绿后以「等待基线合入」挂起全链——下游开工不需要 commit，工作区改动即生效，合入只是提交窗口的批量动作）。**无依赖分支 ≥ 2 时，拆卡交付须附带调度方案由用户选择，禁止默认静默串行**（交付时机 = 拆卡完成停靠，见 SKILL.md ⑥行——停靠时单分支报拓扑序即可、多分支交三要素方案；用户的「继续」即对所报调度方案的放行）——并行方案三要素：① 并行分组（同组卡互不依赖）；② 每组窗口数（每窗口严格单卡，守单卡 = 单窗口 = 单 PR）；③ 合并顺序（按拓扑序逐组合入；共同修改同一文件的卡归入同组串行，防合并冲突）。用户选串行或环境不支持多会话 → 按拓扑序逐卡执行。**调度方案须标注 review 阻塞面**：每张 `risk: high` 卡阻塞哪些下游卡一目了然（供用户排人审优先级）；等审窗口期 AI 切无依赖分支继续执行，禁止干等。**拆卡拓扑设计**：被 ≥2 张消费卡依赖的前置位卡优先设计为低风险纯定义/配置卡（高风险实现后置叶子化），降低单次人审的停摆面
4. **单源资产先拆卡、消费方 depends_on 指向它**——本次需求中被 ≥2 张消费卡共享的底层资产（单源四件套：domain 领域模型、tokens 样式变量、OpenAPI 契约、Adapter 端能力接口，及共享包）各自独立成卡，拓扑序先行；消费方卡 `depends_on` 指向对应单源资产卡；**禁止把单源资产的定义/增改混进第一张消费卡**（单源与消费同卡会让后续消费方卡随手改契约，边界门禁与单源纪律在执行层失效）。互不依赖的多张单源资产卡可并行
5. 高风险卡（资金/鉴权/迁移/删除）标注 `risk: high`，禁止 AL2 自主执行；编码+测试完成后置 `review` 等人审，**禁止自行置 done**——人审通过（执行进度登记批准人+时间）后方可转 done（done 语义由 `assets/task-done-gate.sh` 机械校验；先标 done 后补证据的时间窗 = 虚假状态）。**置 review 必须随即发出人审请示（禁止静默挂起）**，材料包五件：① 逐条 AC → 证据对照（## 验收 节既有内容）；② 本次 diff 文件清单 + 关键改动摘要；③ 按 ## 监督策略 声明的人审焦点逐条自查结论 + 显式声明机械验证未覆盖项；④ 明确的「审完请做什么」（通过 → 登记批准人+时间转 done 并解堵下游；打回 → 按评审意见修复后重新请审）；⑤ 变异报告（行为卡必附：mutation-gate 存活率数字 + 超阈值说明；项目显式豁免或基线期未满时附豁免/基期声明；纯资产变更不计入行为文件、不触发——口径见 gates.md 测试骨架先行节；人审断言强度以此为准，替代逐行肉眼审断言；判据见 gates.md 断言强度门禁节）。人审审的是机械验证覆盖不了的：断言语义真伪、竞态/金额精度、越界与安全（人审三焦点见 gates.md）——AI 不得以自验替代人审（验收证据是 AI 自产的，自证无效），但须以材料包把人审成本压到抽查深度
6. 每张卡自带测试要求——行为变更卡（边界覆盖行为文件）必须在 `## 测试文件清单` 声明看护测试文件，"AC↔测试对应性"门禁（`assets/ac-coverage-check.sh`）强制：清单条目存在且为测试文件、`spec_ac` 不含幻觉引用。断言语义是否真对应 AC 归人审三焦点（防"只断言状态变了"的弱断言）。**测试文件清单的任何变更（新增/移位/聚合/改名）必须同步修正「## 边界」boundary，保证测试文件位于卡边界内（boundary-check.sh 对边界外文件报越界），并在「## 卡内修订」节说明**。项目登记集成标记约定后（AGENTS.md integration-mark 块），**risk: high 行为卡的清单须含 ≥1 个集成标记测试条目**（ac-coverage-check --integration-mark 强制；集成测试骨架允许占位——断言先写、环境配置后补；禁 mock 主依赖为项目 R 规则红线，判据见 gates.md 第二层）
7. 仅写任务卡不授予编码权限；开始实现前核验已有开工授权。拆卡或实现中发现新增触线条件，记录在「## 卡内修订」节并转走门；Spec/HLD 修订影响本卡时置 `blocked`，同步后按当前模式核验适用批准，再继续。
8. **UI 需求的前置卡与页面卡开工门槛**：携带 UI 视觉输入的需求，四件套前置卡（设计规范 Token / 图标清单 / 页面布局规格 / 页面-REQ 映射，判据见 `prd-constitution.md` 第九节第 9 条）先于页面卡拓扑序交付，页面卡 `depends_on` 显式指向对应前置卡；前置产物未过机械校验前页面卡不得开工。页面卡实现只读消化规格（`ui-specs/`），不读原始视觉输入。**页面卡开工三门槛（缺一不得开工，结果登记执行进度 ui-gate）**：① 对应页面规格 frontmatter `digest: quantified`（逐项量化完成；清单级页先补消化，门槛可按页校验：`ui-pack-check.sh <目录> --require-digest p-<序号>`）；② 卡内 `## UI 规格摘录` 完成（**全量摘录 + 覆盖率 N/M 登记**，编码对照纪律见该节注释——厚规格必须对照开发，禁止摘要式摘录后自由发挥）；③ UI 四件套机械校验通过。**页面视觉验收逐卡内联**：页面卡实现完成即对该页执行视觉验收（HTML 路线 = 冻结原型重跑基准 + pixel-diff ≤ PRD 阈值；设计稿路线 = 结构化断言），超标即打回本卡（HTML 路线超标后的修复节奏与停止条件见 `ui-spec-guide` 第四节「HTML 路线 pixel-diff FAIL 修复闭环」——先归因后修改、逐轮差异率登记本卡执行进度、连续 2 轮无下降即停）；D0/CI 为全量复跑与收尾，**不得以 D0 终验替代逐卡内联**（终验发现偏差时返工面已扩大到全部页面）。注意与拆卡规则 4 的"单源四件套"（domain/tokens/OpenAPI/Adapter）是两个不同概念，互不替代——UI 消化产物由 UI 规范管线产出，非本次代码开发拆出。**验收铁律随卡流转**：页面卡派发子代理/新窗口执行时，调度 prompt 必须携带验收条款原文摘录（本条三门槛 + ui-gate 合法格式 + 逐卡内联验收），规范 → 卡 → prompt 逐级"原文在场"而非"精神在场"——禁止只传卡 ID 让下游凭记忆重建条款（实战教训：会话早期加载的规范到执行时已不在有效注意力，重建靠"记忆中的卡片形状"）
9. **页面卡的排除项与菜单对账前置**：在第 8 条三门槛之上另有两项——① 「## 排除项检查」节完成：本卡关联 PRD 册次非目标表逐条核对，命中永久排除/未解禁推迟项禁开工；② 卡触碰菜单/路由/侧栏结构（边界含路由注册表、菜单或导航组件，或增删页面）时「## 菜单/入口对账」节必附 `menu-recon-check.sh` 结果——菜单结构以 ui-specs 中 entry 含 menu 的页面清单为唯一正源（宪法第九节第 12 条），实现不得自造菜单项。文案覆盖率断言（ui-spec-guide 第三节第 7 条）结果记入执行进度 ui-gate 行
10. **观测采集落点完备性**——HLD「观测与灰度声明」节的观测指标表若存在，其声明的采集落点文件须被至少一张卡的「## 边界」认领（通常并入对应行为卡，或单拆埋点卡）；无卡认领 = 拆卡不完整，禁止开工。HLD 免填本节（直通单卡精简路径 / 本章无内容）时不适用本条

## 反例（来自实战）

- 38 个文件的"新模块 bootstrap"= 8~12 张卡，不是一张
- "实现切面 + 全量生效"应拆为：骨架卡（含生效范围控制/试点模块）→ 脱敏卡 → 输出通道卡 → 放量卡
- 高风险卡验收含"实现须 100% 人审"，AI 测试跑绿即标 done、人审至今未发生——done 是虚假状态，合法最高态是 review
- TASK-017"31 页挂载冒烟"先标 done 后补证据（时间窗内验收项为空），且补的测试只断言"组件可加载"，连逐页挂载都不算达标
- 验证证据填一行汇总（"mvn package 通过，N 测试全绿"）替代 ## 验收 逐条对照——done 语义被"我认为完成了"填平，批量 stamp 每卡 1 个动作完胜逐条验收的 3~5 个动作，速度偏好再次战胜纪律
