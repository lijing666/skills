# PRD 编写宪法（通用部分）

> 用途：编写 PRD / 需求文档 / 需求变更时的强制规则。撰写任何需求文档前必须先读本文件；本文件与 PRD 模板冲突时以本文件为准。
> 来源：用户《需求编写宪法》v1.0（2026-09-23，李晶）通用化改编——项目特定流程（如 OpenSpec）归项目级 AGENTS.md 约定。

## 一、文档定位铁律

1. 需求文档只回答 **What**（做什么、做到什么程度），不回答 **How**（怎么实现）。
2. 架构、数据流、API 设计、DDL、算法细节一律放入技术方案文档（hld），需求正文用 REQ-ID 引用。
3. 一个需求变更 = 一个独立文档/change，禁止混合多个不相关主题。
4. 完整 PRD 中无内容章节写 `本章无内容：<原因>`，禁止留空或删除章节。单卡且不触线的轻量 PRD 可按 `prd-template.md` 的轻量必填项省略其他章节；涉及 LLM 的质量与安全要求仍适用。

## 二、句式规范（措辞层）

1. 需求条目必须使用 **EARS 句式**或其变体，按条件类型选择：

   | 条件类型 | 句式 |
   |---|---|
   | 事件触发 | `WHEN <触发条件> THE SYSTEM SHALL <系统行为>` |
   | 分支 | `IF <条件> THEN THE SYSTEM SHALL <行为>` |
   | 持续状态 | `WHILE <持续状态> THE SYSTEM SHALL <行为>` |
   | 范围约束 | `WHERE <约束范围> THE SYSTEM SHALL <行为>` |

2. 每条需求必须附带至少一个验收场景，格式固定（与 jjspec Spec 的 AC 同源）：

   ```markdown
   #### Scenario: <场景名>
   - GIVEN <前置状态>
   - WHEN <动作>
   - THEN <预期结果>
   - AND <补充断言>
   ```

3. 禁止模糊量词：快、慢、友好、高效、稳定、灵活、支持大量、尽可能、一定程度上。
4. 所有性能/质量指标必须量化——数字 + 单位 + 条件。示例：`P95 响应 < 500ms（1000 并发下）`。
5. 待澄清处统一标注 `[NEEDS CLARIFICATION: <具体缺什么>]`，禁止留白或自行编造。

## 三、编号与追溯

1. 需求编号 `REQ-<模块>-<三位序号>`（如 `REQ-GROUP-001`），全文唯一，作废不复用。
2. 非功能需求用 `REQ-NFR-xxx`，成功标准用 `SC-xxx`，用例用 `UC-xxx`。
3. 每条 REQ 必须标注优先级 P0/P1/P2；**P0 占比默认不超过 40%**——全是 P0 等于没有优先级。确属刚需超出时（如合规整改、热修发布），**禁止降级凑数**，必须显式说明理由——把例外摊在明处，而不是把优先级改假。
4. 验收标准、测试用例必须与 REQ-ID 一一映射。
5. 交叉引用一律写 ID（REQ-xxx / UC-xxx / SC-xxx），禁止"如前所述""见上文""同上"。

## 四、边界与非目标

1. 每份 PRD 必须包含**非目标**章节，每条格式：`条目 | 类型（推迟项/永久排除）| 理由`。
2. **无解/失败场景必须显式建模**：写明触发条件、系统行为、用户所见、降级方案。禁止只写 happy path。
3. 列举必须封闭；无法封闭时标注 `开放列举（持续补充）`，禁止用"等""诸如此类"收尾。

## 五、结构与表达

1. 能用表格不用段落，能用列表不用散文；表格必须有表头。
2. 缩略词首次出现必须给全称（如 `LLM（Large Language Model，大语言模型）`）。
3. 自创术语必须在术语表登记，并标注"非行业通用术语"。
4. 假设必须显式列出（假设清单附录），禁止隐含假设。
5. 每章开头用一句话说明本章目的。

## 六、图的规范

1. 禁止以图片（png/jpg/截图）作为任何信息的**唯一载体**。
2. 交互流程、状态机、时序 → Mermaid 代码块。
3. 数据模型 → DDL 为真相源，`erDiagram` 由 DDL 生成，仅作人眼视图。
4. 用例 → 表格（`用例ID | 参与者 | 用例 | 关系 | 优先级`），不画 UML 用例图。
5. 确需评审用视觉图 → 放附录或 HLD，正文保留等价结构化文本。

## 七、AI/LLM 功能的特有要求

LLM 相关功能必须定义以下五项，缺一不可：

| 项 | 说明 |
|---|---|
| 输入输出契约 | prompt 模板、输入 schema、输出 schema、超长/非法输入处理 |
| 失败兜底 | 超时、格式错误、幻觉输出时的重试/降级路径 |
| Go/No-Go 门槛 | 上线的量化指标门槛（如准确率 ≥ 90%，评测集通过率 100%） |
| 评测集 | 评测样例来源、规模、覆盖维度 |
| 安全边界 | 数据边界、PII 处理、prompt 注入防护要求 |

## 八、流程与校验

1. 新需求须走「提案 → 评审 → 定稿 → 执行 → 归档」流程；PRD 定稿只能由用户指令触发，进入下游前校验当前版本的定稿有效，编码另须已有开工授权。直通模式的 Spec/HLD 可保留 draft 进入拆卡与实现；走门模式须先由用户批准当前 Spec/HLD。仅恢复既有约定行为的缺陷修复可免新 PRD，以引用原规格/契约/用户确认预期的修复 Spec 为输入，风险分级与批准要求不豁免。项目使用特定变更工具时，按项目 AGENTS.md 执行校验。
2. PRD 定稿后向下拆解：每条 REQ 转为一张（或一组）任务卡的 Spec——Scenario 块原样迁移为 Spec 的 AC；失败/降级场景转为独立 AC。附C 约束中的新增规则在获开工授权后、编码前落实到 AGENTS.md 或 ADR；仅文档任务只记录建议。
3. **变更工件落点（推荐约定）**：进行中的变更收纳于 `changes/<需求ID>/`，按适用范围放 prd.md（新需求定稿载体：draft → 评审中 → 已定稿；分册需求另含模块分册 `prd-<两位序号>-<英文短名>.md`，结构与拆分规则见 `prd-splitting.md`）、spec.md、hld.md、`tasks/TASK-<编号>.md`（**一张卡一个文件**，编号与卡 id 一致）；纯缺陷修复无需补空 PRD。该目录只放进行中的变更，已完结的必须归档。PRD 原件随归档保存，归档时经资产基线检查反馈到 `docs/PRD.md`。禁止把多张卡并进单个 tasks.md——边界导出按卡文件定位，多卡混放会合并放行。
4. **文档命名规范（两层同构，大小写分层）**：产物文档的**类型词**全局只用五个——`prd` / `hld` / `spec` / `tasks` / `adr`，**禁止同义异名**（design、架构文档、方案文档等一律不作为类型词）。
   - 资产层 `docs/` 文件名大写：`PRD.md`（产品需求）、`HLD.md`（基线架构）、`SPEC.md` / `TASKS.md`（**存量补写场景专用**：需求已实现、从代码反推规格时人显式要求才生成，AI 不自动产出）
   - 过程层 `changes/` 文件名小写：`prd.md` / `prd-<两位序号>-<英文短名>.md`（分册需求）/ `spec.md` / `hld.md` / `tasks/TASK-<编号>.md`
   - 同一文档跨层同名、仅大小写不同（hld ↔ HLD），看到文件名即知层位
   - 归档快照的归宿只有 `changes/archive/`，**禁止复制进 `docs/`（双源）**
   - **五词约束的是文档类型，不排斥带编号的实体文件**——显式例外：`changes/INDEX.md`（能力编年导航）、`adr/ADR-<编号>-<标题>.md`（决策记录）、`tasks/TASK-<编号>.md`（一卡一文件）、`prd-<两位序号>-<英文短名>.md`（分册需求模块文件，规范见 `prd-splitting.md`）、`changes/archive/<日期>-<需求ID>/`（归档快照保留原名）、`ui-specs/`（UI 规范资产目录，结构见第九节第 10 条）
   - **`SPEC.md` / `TASKS.md` 是某版本的规格快照，不是活文档**：须标注补写基准版本/日期；后续行为变更查 `changes/INDEX.md` 与归档 Spec，**不回写本文件**（回写即 OpenSpec 式活文档税，本体系不采纳）
5. **归档三步仪式**（变更验收合入后执行，一步不可省）：
   - **执行判据**（机器可查，违一即归档未完成）：前置闸——开工前 `git status --short` 非空即停，先处理散件或此前中断遗留的 staged rename / 空目录（中断不留痕，status 是唯一线索），归档是对已合入事实的快照，不与未提交修改混提；① 后 status 须全为 R 且无 M 残留（Edit 过的文件先 `git add` 再 `git mv`——git mv 的 index 条目内容取自暂存区，后补的 Edit 会甩在新路径上漏出 commit）；终检——归档 commit 提交后 `git status --short` 必须为空，非空即未完成，禁止汇报完成。
   - ① **移动归档**：`git mv changes/<需求ID> changes/archive/<YYYY-MM-DD>-<需求ID>`——过程可追溯，回流复盘的原材料；
   - ② **INDEX 登记**：在 `changes/INDEX.md` 加一行 `| 日期 | 需求ID | 标题 | 影响能力 | 入口 |`（入口指向归档 Spec 与相关 ADR；分册需求指向归档目录内的主 `prd.md`）——能力编年导航，**纯指针不复制内容**，无双源风险；
   - ③ **资产基线检查**（双检查）：a) **PRD**——本次需求是否触碰目标/非目标翻转、用户角色、成功标准？触碰 → 反馈到基线 `docs/PRD.md` 对应章节 + 版本表加一行（注明来源需求 ID；基线不存在则创建）；b) **HLD**——是否改变系统架构基线（模块增删、数据流变化、接口契约变更）？触碰 → 更新 `docs/HLD.md` 对应章节；未触碰 → 不动。**spec / tasks 不回流**（一次性执行合同，archive 即归宿；能力编年由 INDEX 承载，设计决策由 ADR 承载）。PRD 与 HLD 都只记边界级/架构级修订（低频），行为级演进由 INDEX 逐变更承载——两种变化速率各归其位，行为规格不回写基线（那是 OpenSpec 式活文档的税，仅"行为即合同"的项目按项目级约定选用）。

### 修订与批准有效性

- PRD 目标、AC、非目标或关键约束发生语义变化：增加版本，status 回到 `评审中`，旧定稿不再授权新内容；用户批准当前修订后才恢复 `已定稿`。纯排版/错字且不改变含义时保留定稿，在版本表说明性质。
- 检查受影响的 Spec/HLD/任务卡：在原文件标记待同步，撤销受影响的旧 `approved`，暂停对应实现；同步后按当前模式继续，走门须重批。仅改技术方案而未改产品约定时，不强制重开 PRD，但影响原批准的设计取舍/接口/边界时须重审方案。
- 拆卡、实现及续接时复查风险：风险区、跨模块接口、全局运行时行为、schema 迁移/不可逆变更、金额/幂等/并发或预计至少三张卡，任一命中即转走门。记录新增理由，先起草或修订方案并等批准，再继续受影响工作。
- 批准记录须对应具体文件与版本，记录用户、日期及可追溯消息引用或原文摘要；不能把其他问题上的“可以”算作本方案批准。已有批准对当前版本仍有效时直接续接，不重复索批。

### 跨会话续接（写入现有工件）

- 新需求在 `prd.md` 的“变更续接”区维护当前阶段、模式与理由、已有授权范围及来源、下一步与阻塞；免 PRD 的缺陷在 `spec.md` 维护同一区块，其他文档仅引用，不复制。此区仅记本次变更事实，不写机制或集中台账。
- `status` 表示文档定稿/审批状态；阶段表示待定稿、待开工、待方案批准、拆卡、实现、验收、观测或完成。已定稿不能推导已授权开工，`draft` 不能推导尚未实现。开工授权与方案批准分别记录，用户同句给出时可同时登记。
- 续接先核对当前版本及批准记录，再读取相关 HLD、任务卡、Git/PR 和验证结果；根据证据更新阶段与下一步。存在缺失或冲突时先核实，不自行补造批准；尚有效的用户授权持续有效。
- 开工首次记录带时区的 `started_at`（实际进入 Spec/方案/实现执行段的时刻），续接或返工不重置；仅写文档不设置。任务进度与 PR/验证证据留在对应任务卡。

## 九、UI 真源绑定（携带 UI 视觉输入的需求）

1. **触发**：需求携带 UI 视觉输入（HTML 原型等可实跑渲染的输入，或 Figma 等设计稿）时适用本章；无 UI 需求不适用。位图截图（PPT / PNG 导出）不是可执行真源，仅作人工参照。
2. **真源仲裁**：布局与视觉以视觉输入为准（设计稿路线以消化后的页面布局规格为载体）；文案与字段以视觉输入文本提取为准；行为与业务规则以 PRD 为准。三方冲突登记到附 D 或变更续接，禁止静默裁决。
3. **原型冻结**：编码开工前在 PRD 登记视觉输入的路径与内容哈希（设计稿路线冻结消化产物包，见第 9 条）；冻结后视觉输入再改动视为新变更需求，视觉基准须重建并重受影响验收。
4. **全局视觉验收约定块**：带 UI 原型的 PRD（主文档）必须包含该块，约定三组验收 AC，拆卡时逐卡落卡：
   - 行为组：本 PRD Scenario 原样迁移（同第八节的 Scenario 原样迁移规则）；
   - 视觉组：实现页面与视觉基准的对比验收，**验收方式按第 9 条分支执行**——HTML 原型路线为逐像素对比（阈值量化：数字 + 单位 + 条件，如差异像素 ≤ 0.5%）；设计稿路线为页面布局规格的结构化断言，不使用像素对比（见第 9 条）；采集条件（固定视口、固定 mock 数据）见第 5 条；
   - 状态组：default / hover / focus / active / loading / disabled / empty / error / permission-denied 逐态验收；视觉输入未覆盖的状态（加载、错误、空态等）在 PRD 补规格，不得留给实现自定。
5. **视觉基准生成（HTML 原型路线）**：所有路线的视觉验收采集（截图、结构化断言取值）一律使用固定视口与固定 mock 数据；视觉基准必须由原型 HTML 在浏览器实跑渲染生成（同视口、原型自带演示数据，如 Playwright 截图）；禁止以存量截图作为 diff 基准——可能已过时，构成双真源。基准文件属于视觉规格：修改基准 = 修改需求，须走批准留痕（建议列入项目 AGENTS.md 风险区清单）。设计稿路线的基准与验收方式见第 9 条。
6. **验收映射加列**：第 8 章验收映射表统一含「UI 真源」列，格式 `P-<编号> <页面名>（原型锚点）`；无 UI 需求或纯后端 REQ 统一填「—」；原型未绘制的空页面对应 REQ 填「空页面-新设计」，免视觉组，改走设计系统合规验收（Token 与状态覆盖检查）。
7. **分册需求**：全局视觉验收约定块由主 PRD 承载（并入分册规范的全局章节独占清单）；全部模块分册第 8 章同步加列；拆 Spec 时按映射表把三组 AC 落到对应页面卡。
8. **存量 PRD 补挂**：用户指定已有 PRD 补挂时，按本文件修订规则执行——版本 +1、回评审中、版本表登记修订来源；禁止静默修改已定稿 PRD。
9. **前置产物四件套**：带 UI 视觉输入的需求，拆页面卡之前须先产出四份封闭列举的消化产物，作为 UI 任务卡 DAG 的前置卡交付；AI 实现时只读这份消化规格，不读原始视觉输入：
   - 设计规范：Token 文件（颜色、排版、间距、圆角、阴影、布局尺寸）+ 规范文档，取值从视觉输入机械提取（HTML 路线取实跑渲染的 computed styles；设计稿路线取设计稿标注或 API 导出）后语义命名，不凭目测抄写；
   - 图标资产与清单：全部图标位的语义 → 指派图标（图标库条目或导出资产文件）的封闭清单；
   - 页面布局规格：逐页量化布局规格（结构、间距、字号、状态）。HTML 路线由实跑 DOM 生成（薄规格）；设计稿路线由设计稿消化生成（厚规格），此时它是视觉真源的正式载体；
   - 页面↔REQ↔素材映射：绑定流程的工作产物（语义识别生成、用户修正后生效），单向回填 PRD 第 8 章「UI 真源」列——PRD 该列是唯一事实源；映射产物收进 `changes/<需求ID>/` 随归档并标注"由 PRD 生成，禁止手改"，落点见第 10 条。
   冻结与验收按输入分支执行：
   - HTML 原型路线：冻结原型文件哈希（第 3 条）；视觉验收 = 与实跑渲染基准 pixel-diff（第 5 条）；
   - 设计稿路线：冻结消化产物包（四件套）整体哈希，原始设计稿后续变更须重新消化再受影响验收；视觉验收 = 页面布局规格的**结构化断言**（computed styles 逐项量化断言，确定性验收），**不使用像素对比**——设计稿导出帧与真实渲染存在系统性差异（字体光栅化、dpr、平台原生组件、动态数据），无法支撑还原口径的 diff；导出帧仅作人工对照参考，不入规范包、不作 diff 基准。
   四件套均须可机械校验：Token 覆盖率核查（判据与算法见 `references/ui-spec-guide.md` 生成管线机械校验步）、图标与组件引用不出清单（lint 执法）、布局规格断言入测试。前置产物未产出并通过校验前，页面卡不得开工。
10. **产物落点与命名**：UI 规范产物统一放工作区根 `ui-specs/`（与 `changes/` 平级；tokens/icons 属代码资产，开工后由项目 AGENTS.md 声明仓库引用方式），按**业务大项**分目录，结构固定：
    - `ui-specs/<产品ID>-<业务大项>/`（kebab-case，如 `yzz-admin`、`yzz-miniprogram`）
    - `README.md`——入口：frontmatter（type: ui-spec）+ 版本表 + 冻结哈希 + 页面索引 + 未决项
    - `tokens.<css|scss|json>`——Token 文件，实际扩展名在 README 登记
    - `icons/`——`icons.json` 封闭清单 + 图标资产文件
    - `pages/p-<两位序号>-<英文短名>.md`——页面规格，序号 = PRD「UI 真源」列的 P-xx
    - `baselines/`——视觉基准图（二进制，**仅 HTML 原型路线**）：实现阶段（D0/CI）由冻结原型实跑渲染生成（采集条件与"修改 = 修改需求须批准留痕"见第 5 条），规范生成阶段不产出；**设计稿路线不产出 baselines**，理由与导出帧处理见第 9 条
    命名铁则：① 页面规格编号与 PRD「UI 真源」列的 P-xx 一一对应，双向可定位；② 页面规格 frontmatter 记录所属业务大项、关联 PRD 模块草案、视觉输入锚点；③ 页面规格一律纯文本，不嵌截图——截图入 `baselines/`，md 内仅存指向视觉输入的锚点，防止二进制膨胀与双真源；④ 生成与绑定流程的执行细则见 `references/ui-spec-guide.md`。`ui-specs/` 目录为文档命名规范的显式例外（同 `adr/`，登记于第八节第 4 条）。
