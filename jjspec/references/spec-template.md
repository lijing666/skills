# Spec（需求规格）模板与写法

> 用途：编写需求或修复 Spec，方案起草前明确 AC。新需求以有效定稿 PRD 为输入；纯缺陷修复引用原规格/契约/用户确认的预期行为。仅写文档时只读项目规则并记录缺口建议。Spec 是需求与代码之间的可评审中间层。

## 模板

```markdown
---
title: <功能名> Spec
type: spec
status: draft | approved | implemented
version: v0.1
date: YYYY-MM-DD
source_requirement: <PRD 路径及版本；或原规格/契约/用户确认的预期行为依据>
---

## 1. 背景与目标
<3~5 句话：为什么做、解决谁的什么问题>

## 2. 验收标准（AC）——Spec 的灵魂
<!-- Given-When-Then 格式，写到"可测试"为止。每条 AC 必须能映射到至少一个自动化测试 -->
- AC1: Given <前置状态> When <动作> Then <可观察、可断言的结果>
- AC2: ...
- AC4: <并发/时序陷阱必须显式写成 AC——AI 不会主动想到，但给了标准它能写出正确的测试>

## 3. 非目标（防范围蔓延——AI 编码头号事故源）
<!-- 不做什么。AI 特别热衷顺手"优化"相邻代码，非目标是它的围栏 -->
- 不支持 <X>
- 不改动 <Y>

## 4. 边界约束
<!-- 项目级硬约束引用，不重复定义 -->
- 金额计算禁止浮点（R 编号/ADR 引用）
- 支付回调幂等（沿用既有幂等框架）
- <模块依赖方向约束>

## 5. 风险与开放问题
- <已知风险、待定决策>
```

## 写作规则（自查清单）

1. **出现"等等"= 边界模糊** → AI 会自由发挥，必须枚举穷尽或移入非目标
2. **AC 不可测（"体验要好"）= 门禁失效** → 改写为可断言的观察结果
3. **没有非目标 = 范围蔓延** → 必写，哪怕是"不改动普通订单流程"这种一句
4. **AC 数量参考**：中等需求 4~8 条；并发/超时/幂等类陷阱各占一条
5. **边界约束只引用项目规则**（R 编号/ADR），不复制粘贴——单一事实源
6. **禁止模糊量词**（快/慢/友好/高效/稳定/灵活/尽可能）——指标必须数字+单位+条件（如 `P95 < 500ms（1000 并发下）`）
7. **失败/无解场景必须显式写成 AC**——禁止只写 happy path；每条失败路径都要有 GIVEN/WHEN/THEN
8. **待澄清统一标注 `[NEEDS CLARIFICATION: <缺什么>]`**——禁止留白或自行编造
9. **交叉引用一律用 ID**（REQ-xxx / AC-n / ADR-xxxx）——禁止"如前所述""同上"
10. Spec 不单独停靠——直通模式可从 `draft` 进入拆卡与实现，随 PR 抽审；走门模式与 HLD 一并交审，批准记录明确本 Spec 版本后置 `approved`。实现与 AC 验证完成后可据证据置 `implemented`，不反推曾获方案批准

> 新需求先经 PRD 定稿，再由 REQ 拆 Spec。仅恢复既有约定行为的缺陷可直接写修复 Spec，必须给出复现与预期依据；现有代码本身不能证明预期。预期不明先澄清，改变产品行为则转 PRD。免 PRD 不豁免风险分级、方案批准或回归测试。
>
> 实现假设以 `[假设]` 标注；改变目标/AC/非目标/关键约束须回 PRD 再定稿。修复 Spec 的预期行为改变时重新确认依据。版本修订与风险复判遵守 `prd-constitution.md`；受影响的旧批准失效时回 `draft` 并停止对应实现。

## 缺陷修复的续接区（仅无 PRD 时追加到 Spec）

```markdown
## 变更续接
- 当前阶段：<待澄清/待开工/待方案批准/拆卡/实现/验收/观测/完成>
- 模式与理由：<直通/走门及依据>
- 授权范围及来源：<仅文档/修复开工授权；用户消息引用或原文摘要、日期>
- started_at：未开工
- 下一步与阻塞：<动作、缺失信息；关联 HLD/任务卡/PR 链接>
```

有 PRD 时直接引用其续接区；无 PRD 时按 `prd-constitution.md` 的续接规则维护上表信息，不另建台账。
