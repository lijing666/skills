# 选型程序（四步选型 + 锚定评分 + 选型三问）

> 用途：跨端 UI 方案 / 共享技术栈选型（uni-app x、Taro、Flutter、React Native、KMP 等）、新端（尤其鸿蒙）可行性评估。产出是选型结论与试点建议；需要保存决策时使用 `assets/tdr-template.md`，文件落点、执行授权和批准遵循当前工作流与项目约定。源自课程 Day 1/Day 4（含 2026-10 学员修订）。

## 复用分层模型（L1~L5，本库全局编号）

| 层 | 位置 | 策略 | 一句话 |
|---|---|---|---|
| L5 表现层 | 端上 | 复用程度是选型题 | 全原生各写 ↔ 统一方案一份编译多端 |
| L4 端能力适配层 | 端上 | 接口一份、实现各端各写 | Adapter 层（规则 R-U05/R-U06） |
| L3 共享业务层 | 端上 | 最大化复用一份 | 跨端语言共享包，各端同源 |
| L2 接口层（契约边界） | 服务端边缘 | 契约唯一 | 统一 API 契约 + BFF 端差异聚合 |
| L1 服务与数据层 | 服务端 | 与端无关 | 业务规则权威裁判 |

复用优先级：稳定的业务逻辑优先复用，平台交互分别适配，UI 复用按体验和维护成本单独论证。架构演进自底向上：先工具库/领域层/API SDK，再考虑 UI 层复用。

统一方案（uni-app x / Taro / Flutter / RN 类）= 框架把 L3+L4+L5 打包成一份共享技术栈、L4 由框架厂商预实现。评估三件事：框架包揽多少、能力边界外补多少 Adapter、极致体验留不留原生逃生舱。

## 四步选型程序

主轴唯一：**先过滤，再比选，再裁决混布**。产品形态与组织背景都不许当硬分叉——前者定必选端，后者是打分项。

1. **列端清单**：全部端列出，分"必选"（不覆盖直接出局）与"想要"；口头要求（"老板要鸿蒙"）按必选对待、标注待查证。
2. **必选端硬过滤**：先列组件的端覆盖表，明确评估的是共享逻辑、UI 还是完整运行栈；仅覆盖部分必选端的技术保留为组合素材，不能单独进入最终评分。可评分候选 = 覆盖全部必选端及关键能力的单方案或组合方案（如小程序用 Taro、App 用 RN，加各端 Adapter）；组合须声明各端落点与集成边界。无法查证的覆盖标为待验证，不当作已支持；可列验证计划，尚不能进入最终可行候选。
3. **同层比选**：只对全覆盖的可行候选打六维分（锚定评分法见下）；组合整体评分须计入多栈维护、集成、排障和发布成本。六维：开发效率 / 性能体验 / 生态成熟度 / 团队技能（会不会审、能不能排障、组织接不接得住）/ 长期维护 / AI 工具适配。先明确权重与总分算法，默认六维等权。
4. **裁决 + 试点建议**：最高分为单方案 → 推荐单方案；为组合方案 → 推荐混布，写清端/页面走哪条栈及共享边界。无全覆盖可行候选 → 报告覆盖缺口，给验证或分期建议，不能自行取消必选端或硬选部分覆盖方案。建议用最复杂真实模块试点，周期按风险与范围估算（4~6 周为参考）；咨询阶段不自动执行试点。结论与退出条件可写入选型类 ADR，试点未完成时状态保持 proposed，实测结论留待验证。

### 锚定评分法三条纪律

1. **锚定打分不凭手感**：先定义 5/3/1 分锚点再打分。例——人才可得性：5 = 团队已熟练 + 市场供给充足；3 = 需 2~4 周学习或招聘 ≤1 个月；1 = 全队没人会 + 市场稀缺。生态成熟度：5 = ≥3 个同规模生产案例 + 活跃维护；1 = 无生产案例或一年无实质提交。
2. **证据打分**：每个分数附一条可验证证据（生产案例 / Issue 活跃度 / Benchmark / 招聘岗位数）——写不出证据的维度按 1 计。
3. **重大选型建议两人独立打分**：分差 ≥2 的维度重点校准；人员不足时标注单人评分的局限，咨询初稿不因缺第二人而阻塞，也不得冒充已完成双人校准。

### 选型三问（比矩阵更重要）

1. **反悔成本是多少？** 语言/框架 = 高反悔成本（花 10 倍时间论证）；库/工具 = 低反悔成本。
2. **谁在用、谁赢了、谁弃坑了？** 找 3 个同类规模真实案例，重点看弃坑者复盘（成功案例有幸存者偏差）。
3. **投降条件是什么？** "当 X 发生时重新评估"必须写进决策记录，禁止留空。

### 鸿蒙支持三档判定（使用时查证）

| 档位 | 查证内容 | 准入处理 |
|---|---|---|
| 官方主线支持 | 当前发布版本的目标平台、运行栈与关键能力 | 覆盖证据充分可进候选，仍需试点 |
| 官方共建/社区主线外 | 维护方、版本兼容、构建链及生产案例 | 声明额外维护风险；覆盖未证实则待验证 |
| 无可验证支持 | 本次需要的层与能力缺少实现证据 | 不能作为该端覆盖依据；可保留为其他端或其他层的组合素材 |

每个判档结论附官方仓库/发布说明、具体版本、目标系统/API 级别与查证日期，不把框架名称固定绑定某档。KMP 逻辑共享与 Compose UI 支持分别查证；逻辑共享不能代替鸿蒙 UI/运行栈覆盖，某层未支持也不淘汰覆盖其他端的组合素材。鸿蒙关键能力仍须试点实测。

### 选型三面红旗

1. "一套代码搞定鸿蒙"的承诺——鸿蒙端必须单独验证。
2. 按"写一份"估算全部人力——单独估算共享实现、各端 Adapter、平台差异、测试与发布成本，不把通用比例当项目预算。
3. 跳过试点直接全面上——试点结论不写 TDR 投降条件 = 没做试点。

### AI 分工

**AI 起草与取证，人确认关键决策**：AI 可查官方资料、起草评分表与退出条件（标注假设），获实施授权后可搭试点；训练数据不能作支持度证据。实际取证与试点结果须留来源、版本和执行记录，人员按当前工作流评审。未经确认的组织假设、最终选型及退出条件保持待确认，不新增与工作流重复的批准停靠。

## 主流方案速查（2026 视角）

| 方案 | 复用范围 | 性能验证重点 | 动态化约束 | 典型适用 |
|---|---|---|---|---|
| 全原生 × N | UI 分别实现，可共享规格/逻辑 | 启动、帧率、资源与平台能力 | 平台审核与分发政策 | 体验极致型（相机/游戏/旗舰 App） |
| H5 混合容器 | Web 内容复用，能力桥接分别适配 | WebView 启动、桥接与离线表现 | 远程内容不等于任意代码热更 | 内容运营型、快速试错模块 |
| React Native 系 | 逻辑/UI 共享，平台模块适配 | 渲染、原生模块与版本组合 | 受平台政策约束 | React 团队、中等复杂 App |
| Flutter | 逻辑/UI 共享，平台插件适配 | 渲染、包体与插件 | 受平台政策约束 | 全新多端产品、UI 密集型 |
| KMP / Compose MP | 逻辑与 UI 分别评估覆盖 | 目标端编译链与平台互操作 | 目标平台政策 | Android 为主、逻辑复用优先 |
| uni-app x / Taro 类 | 按版本核对小程序/App/Web 覆盖 | 各目标运行时与插件能力 | 平台审核与运行时限制 | 小程序为主的产品候选 |

注意：微信小程序是独立体系（独立运行时、双线程、审核分发），与 Web 不天然一体——小程序的正确待遇 = 一个必选端进入第 2 步过滤条件。
