# 端能力矩阵表（模板 + 用法）

> 用途：新功能可行性输入、Adapter 验收清单与端期望管理。使用 jjspec 时作为 `docs/HLD.md` 或本次 `changes/<需求ID>/hld.md` 的能力矩阵节维护；已有独立矩阵时引用其正源，不复制第二份。其他项目遵循既有文档约定。列仅含实际端与已确认规划端，未触能力时不新增独立文档。

## 模板

| 能力 | 实际端 A | 实际端 B | 已确认规划端 C（若有） | Adapter 接口 | 验证证据 |
|---|---|---|---|---|---|
| <本需求触达能力> | 待验证 | 待验证 | 未排期 | <项目已定接口或待设计> | <目标 SDK/版本/设备 + 测试记录> |

填表约定：

1. 格子四态：已覆盖（可注降级方式与实测证据）/ 待验证 / 不支持（附目标平台或项目实现限制）/ 未排期；不把未实现写成平台不支持，不把模板示例写成已验证结论
2. **降级是正常态**：某端不支持时写降级路径（如 Web 扫码降级为手动输入）——"某端不支持"是正常分支而非异常
3. 平台差异写进备注（如不同商品/地区支付候选、推送通道）；依赖政策的结论附官方依据与查证日期，业务语义差异写进契约

## 用法纪律

1. 待验证格就是试点清单；AI 或人工均只能依据目标环境实测、契约测试与可追溯记录改为已覆盖，训练数据和文档印象不能替代实测。引用已有有效实测记录不必重复试点
2. **新功能立项先查此表**：功能触达的能力行 × 目标端列，空格子 = 排期依据
3. Adapter 验收：新能力新增一行，先复用已有语义接口，确有缺口才新增接口；改为已覆盖须目标端实现/降级可用并有契约场景验证
4. **新需求不触达任何能力行 → 能力矩阵无新增行、Adapter 零改动**——这个"零"要显式写进架构文档（零改动是显式结论，不是遗漏）
5. **接入新端 = 新增一列**：逐行评估该端等价物，这就是"鸿蒙工作量 ≈ 一个新端"排期结论的量化来源
