# 通用规则（R-U：按需求与工程前提适用）

> 用途：架构设计时按本次需求对照，体检时先判断适用性。支付、服务端、高并发、缓存、monorepo 等规则仅在对应业务或工程前提成立时适用；不存在的端与能力不因此新增。项目既有契约/ADR 优先，冲突列开放问题并按工作流处理，不静默迁移。落位可同时包含 AGENTS.md / HLD / 契约 / CI。规则源自《全栈架构师九天教程》，本次修订补充工程适用边界。

## 分层与落位

### R-U01 通信只经契约
- 规则：前端侧与服务端的一切通信只经由 L2 契约边界，禁止绕过契约直连 L1（服务与数据层）。
- 落位：HLD·分层裁决表；AGENTS.md·分层禁区。
- 违反信号：端代码直调服务端内部接口 / import 服务端内部模块。

### R-U02 裁判权在 L1
- 规则：涉及服务端交易、权限或共享业务事实时，权威裁判在 L1；L3 只做非权威预判与镜像，冲突以已验证的服务端结果纠偏。纯本地或离线业务按已确认的本地真值与同步规则设计，不为套分层模型新增后端。
- 落位：HLD·分层裁决表；AGENTS.md·分层禁区。
- 违反信号：端上独立实现交易式校验且无服务端复核；各端各裁同一规则。

### R-U03 分层裁决表
- 规则：涉及业务逻辑分层的 HLD 含裁决表——每条逻辑一行（逻辑/权威落点/理由），权威落点唯一；逐条回答裁判还是预判、真值在哪、是否触达平台能力、呈现是否平台惯例。镜像/预判在理由中注明，不作第二权威。
- 落位：HLD·分层裁决表（骨架见 references/hld-injection.md）。
- 违反信号：Spec 验收标准涉及的逻辑在裁决表无对应行。

### R-U04 状态分层
- 规则：客户端状态分三层各住一处——①服务端查询缓存：有服务端真值的数据用查询缓存层管理并与服务端保持同步，禁在全局 store 手写副本双写 ②跨页客户端共享状态：纯端上产生、跨页使用，进全局 store ③页面局部状态：组件内。按序取用：能用 URL 就不用全局，能查询缓存层就不本地复制，能局部绝不提升。
- 落位：AGENTS.md·分层禁区；HLD·分层裁决表。
- 违反信号：服务端真值数据在全局 store 手写副本；本地副本与真值双写。

### R-U05 Adapter 零新增判据
- 规则：平台能力（相机/推送/支付/传感器等）必须经 L4 Adapter 接口访问；不触平台能力的需求 Adapter 零新增，"零改动"必须显式写进 HLD 工程化落位节。
- 落位：HLD·工程化落位；AGENTS.md·分层禁区。
- 违反信号：纯逻辑需求出现新 Adapter 接口；HLD 缺"零改动"显式结论。

### R-U06 Adapter 五规范
- 规则：①接口按业务语义定义（`scanCode()` 而非 `openCamera(config)`）②返回值含 isSupported 能力协商与降级路径 ③权限统一建模（ensurePermission(cap)，各端映射到自己的权限机制）④实现归各端、接口定义归全栈评审 ⑤新增端 = 新写一组 Adapter 实现，业务层零改动。
- 落位：HLD·Adapter 接口设计；契约资产·adapter 接口单源。
- 违反信号：接口名含平台专有词；返回值无能力协商。

### R-U07 共享三档与生成物禁手改
- 规则：跨端共享按三档取最强可行档：源码共享 > 规格生成 > 测试拴住；二档及以上"人只改单源，生成产物禁手改"；可移植性验收标准 = 新端接入业务层零改动。
- 落位：AGENTS.md·禁改目录清单；流水线·CI（生成产物 diff 检查）。
- 违反信号：直接编辑生成的 SDK / tokens 产物；新端接入需重写业务规则。

### R-U08 支付渠道三层裁决
- 规则：支付候选集由 L1 按端、商品、地区及当前平台政策裁决；iOS 数字商品默认核查 IAP 要求，获准例外必须留官方依据与适用范围。客户端可提交用户选择的渠道标识，但服务端必须校验其在候选集内并创建支付单，不能信任端上传的金额或权益。SDK 同步结果不能决定发放权益，以服务端验签并幂等处理的支付状态为准。
- 落位：HLD·关键流程；契约资产·支付接口。
- 违反信号：服务端不校验端选渠道；无当前政策依据采用支付路径；客户端凭 SDK 回调直接发权益。

### R-U09 iOS 平台费合规
- 规则：权益挂自建账号；iOS 定价、外部购买链接和文案须按实际地区、商品、entitlement 与当前 App Store 政策核查，方案记录官方来源、查证日期与适用范围，不把某地区结论推广到全部地区。跨端充值入口仅在产品已确认范围内设计。
- 落位：HLD·商业与合规。
- 违反信号：未核查适用政策就承诺外部购买引导；无依据扩大充值入口范围。

### R-U10 能力矩阵纪律
- 规则：能力矩阵按真实目标端与项目实现维护；待验证转已覆盖须有目标环境实测/契约测试记录，AI 与人工都不能以训练数据或文档印象代勾。已有有效实测可引用，不必重复试点；未排期与平台不支持分开。
- 落位：HLD·能力矩阵与一致性分级（空白表 assets/capability-matrix.md）；AGENTS.md。
- 违反信号：待验证格在无有效实测或契约测试证据时被填成 ✅。

### R-U11 设备同步拓扑
- 规则：服务端权威的跨设备状态优先采用中心同步；离线/本地优先与硬件协作按实际要求评估直连或合并协议。跨设备状态均声明权威来源、强/最终一致、冲突裁决与恢复策略；中心拓扑不消除并发写冲突。
- 落位：HLD·关键流程。
- 违反信号：跨设备状态无冲突裁决设计；设备间互为真值。

## 契约与 BFF

### R-U12 契约单源
- 规则：每个有界业务域的同一公共契约只有一个权威来源，可有独立版本；端家族契约的领域语义从权威契约派生且可追溯，不把全公司所有领域强合成一个 schema。
- 落位：契约资产·OpenAPI；HLD·接口设计。
- 违反信号：同一接口两处定义；端家族契约改动追溯不到领域契约。

### R-U13 一致性四件套
- 规则：L1 裁决 → 契约告知（结果字段与语义显式进契约）→ 本次受影响端按契约呈现 → 对应场景测试锁定，四件缺一不可；未排期端不要求实现或跑测试。
- 落位：HLD·接口设计与关键流程。
- 违反信号：规则变更未同步契约字段；新契约无对应场景测试。

### R-U14 API 硬规范十条
- 规则：①HTTP API 沿用项目版本策略，破坏性变更须有版本/兼容迁移方案（`/v1/` 为示例）②REST 接口资源名词复数、动词走 HTTP 方法；其他协议遵循其契约 ③列表分页/排序/过滤按场景声明，游标优先但可解释采用偏移，禁各端自造参数 ④项目统一错误结构与错误码（示例 `{code, message, request_id, retryable}`）⑤时间带明确时区，金额整数最小单位 + 货币枚举（不把所有币种都按分）⑥需重试保护的非幂等写操作声明幂等键/状态机，天然幂等操作注明依据 ⑦契约先行并按当前工作流评审 ⑧响应最小化且权限过滤，BFF 裁剪仅在已有 BFF 时适用 ⑨长任务声明异步查询/通知协议 ⑩变更通知按平台与可靠性评估推送或有界轮询（间隔、退避、停止条件），不强制新增推送基础设施。
- 落位：契约资产·OpenAPI；HLD·接口设计。
- 违反信号：接口评审清单任一条不过。

### R-U15 移动端流量预算
- 规则：面向 App/H5 的接口依据目标网络、首屏与数据形态设响应体积/分页预算，并明确压缩前后口径；50KB 响应、10KB 核心列表、20 条分页仅为起步参考，媒体/下载等接口单独分档，阈值由项目确认。
- 落位：契约资产·接口评审清单。
- 违反信号：无项目预算基线；超出已确认预算且无降级或豁免依据。

### R-U16 BFF 约束
- 规则：≥3 端聚合需求分化、或多团队并行时才引入 BFF（单 Web 端不需要）；BFF 是薄层只做聚合/裁剪/协议转换，禁写业务规则；按端家族分组（mobile/web/mp，2~3 个足够）不按端一个；BFF 对端也有 OpenAPI 契约。
- 落位：HLD·总体架构；AGENTS.md·分层禁区。
- 违反信号：BFF 代码出现业务规则分支；每端一个 BFF。

### R-U17 BFF 路由显式
- 规则：端到 BFF 路由用显式手段（独立域名或路径前缀）；端标记 header（X-Platform 类）只用于运行时策略（限流/灰度/打点），不用于选 BFF。
- 落位：HLD·总体架构；契约资产。
- 违反信号：网关按 header 转发 BFF。

### R-U18 一致性分级
- 规则：跨端行为分级管理并写成规范：强一致（交易/资金/法务文案——领域层 + 契约）/ 弱一致（视觉与主交互——Token + 组件库）/ 各端特色（平台惯例——强行一致反而伤害体验）。
- 落位：HLD·能力矩阵与一致性分级；AGENTS.md。
- 违反信号：平台惯例交互被抹平；交易字段走弱一致。

### R-U19 强一致兜底在 L1
- 规则：展示价等允许短暂旧，下单时服务端按真值裁决；前端任何缓存策略不为交易正确性负责。
- 落位：AGENTS.md·分层禁区；HLD·关键流程。
- 违反信号：交易正确性依赖前端缓存状态。

### R-U20 发布列车
- 规则：按实际依赖安排发布：先部署向后兼容的服务端/契约，再升级受影响客户端；其余端无依赖时可独立发布，不固定五端先后顺序。兼容性按契约版本矩阵验证，不强制各应用 minor 版本相同；破坏性迁移用 expand/contract 与明确退役条件。
- 落位：HLD·发布与演进；流水线·CI（兼容性检查）。
- 违反信号：破坏性变更先于服务端兼容层上线。

## 数据与高并发

### R-U21 建模三原则
- 规则：①一个业务事实声明唯一权威存储与派生关系 ②查询优化依据执行计划、数据量、索引与延迟预算，多表 JOIN 不是单独违规条件；必要时评估宽表/物化视图/搜索索引及一致性代价 ③一致性边界由业务需求决定，方案写明强/最终一致、异常与恢复条件，按工作流确认。
- 落位：HLD·数据设计。
- 违反信号：同一事实两处真值；无执行计划或指标就禁止 JOIN/新增派生存储。

### R-U22 CQRS 触发判据
- 规则：跨分片扫描或查询影响交易预算时，先评估查询/索引优化，再按收益评估读模型或 CQRS（读写模型分离，不必使用不同存储技术）。采用异步派生视图时，业务写入与 outbox 事件同事务提交或用等效可靠机制；消费者幂等、可重放，读视图可重建，声明延迟预算。未出现瓶颈不因有报表就强制引入 CQRS。
- 落位：HLD·数据设计。
- 违反信号：无指标即引入第二存储；异步派生事件先提交事务再发 MQ 且无可靠补偿；读视图不可重建。

### R-U23 缓存三铁律
- 规则：使用缓存前明确一致性与失效策略、负载收益；按风险采用过期抖动、请求合并/互斥重建、负缓存等手段，逻辑过期须有刷新机制，禁无失效的永久旧值。缓存失效须限流/熔断与有界回源，必要时受控拒绝或降级，不要求无限流量直压数据库；承载会话/幂等/预扣的 Redis 与纯性能缓存区分并单独声明故障恢复。
- 落位：HLD·数据设计。
- 违反信号：无失效策略；缓存故障无限回源；将 Redis 中的业务状态当可随意丢弃的缓存。

### R-U24 分库分表红线
- 规则：分库分表先依据数据库版本、记录宽度、索引、硬件、吞吐与延迟预算证明容量/性能瓶颈，再比较优化、分区、垂直与水平拆分。行数或体积经验值仅作调查提示，不作统一硬红线；分片键按已确认的核心查询与扩容需求选择，HLD 写明阈值依据、迁移与回退方式。
- 落位：HLD·数据设计。
- 违反信号：只按固定行数/体积决定拆分；无瓶颈证据；分片键未评估查询与迁移方式。

### R-U25 高并发三板斧前置
- 规则：限流（网关按端+接口+用户三级配额，核心保底边缘先弃）、熔断（依赖超时 + 错误率阈值、半开探测恢复）、降级（预定义开关：非核心可关、读降缓存、写降异步）——三板斧清单提前写进 HLD，不是故障时现想。
- 落位：HLD·风险与降级。
- 违反信号：HLD 无降级清单；熔断无半开恢复。

### R-U26 幂等三层防线
- 规则：非幂等写操作需重试保护时，服务端校验幂等键作用域及请求指纹，可靠记录处理状态/结果，副作用与去重记录须具备事务或等效一致性，重复请求返回一致结果；不能只用易过期 SETNX 锁声称幂等。库存扣减按需用 DB 原子条件更新（`stock >= requested_quantity`）并检查受影响行数；只有已证明存在洪峰瓶颈时才引入 Redis 原子检查与预扣，预扣是流量治理而非幂等替代。天然幂等操作显式声明依据。
- 落位：契约资产·写接口；HLD·关键流程。
- 违反信号：锁过期可导致副作用重复且无持久防线；扣减无数量条件/行数检查；普通写接口被强制加 Redis 预扣。

### R-U27 预扣三纪律
- 规则：仅在采用 Redis 库存预扣时适用：DB 是最终库存权威，预扣记录有唯一业务标识与状态；成功预扣后的失败、取消、超时释放须幂等，拒绝且未扣成功的请求不得回补。对账区分可售、预留、已实扣与已释放的状态；恢复/重建同时核对 DB 与在途预扣，避免遗失预留或重复释放。
- 落位：HLD·关键流程。
- 违反信号：成功预扣无释放路径；重复回补；未扣成功也回补；重建忽略在途预留；无状态对账。

## 工程化与 AI 防线

### R-U28 仓库形态判定（评估对象 = 业务大项）
- 规则：按业务大项两层判定仓库形态。**术语："业务大项"（非行业通用术语）** = 产品内一个独立交付价值的区块，从 PRD 的使用者与端载体反推识别——同一批使用者 + 同一组端载体 = 一个大项；使用本判据时须在项目术语表登记该词并标注"非行业通用术语"。
  - 第一层·逐大项定仓形态（大项识别只依据 PRD 已确认范围，不假设未来大项）：

| 大项类型 | 判定条件 | 仓形态结论 |
|---|---|---|
| 管理后台类 | 使用者均为管理/运营人员，且端载体仅 Web 管理界面 | 常规单仓 |
| 端型 | 端载体含 H5 / 小程序 / iOS / Android / 鸿蒙任一端 | monorepo——当前仅 1 个端也建（结构为后续端扩展预留）；apps/ 放端工程并按各端官方规范组织，不按安装包数机械拆分 |

  - 第二层·端型大项 monorepo 的服务端归属：仅服务该大项（专属 BFF/服务）→ 并入其 apps/api-server；跨大项共享（统一后端）→ 独立常规仓，契约本体住服务端仓，各端 monorepo 的 api-contract 只放生成工件 + CI 漂移检查（R-U38）。
  - 大项内端交付形态（跨端框架一份源码编译多端 vs 各端纯原生）由选型程序（references/selection-program.md）裁决——它只决定 apps/ 内部实现，不改变第一层仓形态结论。设计意图（防误读）：monorepo = 契约与共享层单源容器 + apps/ 各端独立编译发布，仓形态与是否选跨端框架无关；多个业务大项建多个仓是正常结构。
  - 存量工程默认维持既有结构，迁仓单独论证并获相应授权；拆仓与并仓理由写入 HLD 工程化落位节；端矩阵按已确认范围维护，增删/分期均记录依据。
- 落位：HLD·工程化落位。
- 违反信号：端型大项建成常规单仓；多个业务大项并入一仓；服务端工程与端工程并列一仓且不满足服务端归属判定；跳过大项识别直接套 apps/packages 目录；为套结构擅自迁仓；假设未来端并提前建仓。

### R-U29 monorepo 三纪律
- 规则：①影响感知——改共享包时 CI 自动只跑受影响流水线 ②边界执法——app 间禁互引、依赖方向单向、lint 机器化 ③统一任务入口——所有包 build/test/lint 命令名统一。
- 落位：流水线·CI；AGENTS.md·统一命令。
- 违反信号：app 互相 import；各包命令名不一致。

### R-U30 单源四件套（端型大项 monorepo 的 packages/ 结构）
- 规则：端型大项 monorepo 的 packages/ 按两层结构落位；常规单仓（管理后台类/服务端）不套此结构，仅按适用性声明单源落点。
  - 规格契约层（端型大项必建，与当前端数无关）：tokens（Design Token 权威规格，R-U31）· domain-spec（语言无关领域规格单源：业务规则、枚举、错误码、状态机）· adapter-contract（平台能力 Adapter 接口规格，R-U06/R-U37）· api-contract（接口契约；跨大项共享时只放生成工件 + CI 漂移检查，本体住服务端仓）。
  - 语言实现层（按需）：domain-ts / domain-kotlin / domain-swift / domain-arkts、api-client-<端>、adapter-<端> 等实现包，按已确认端与选型结论建；共享实现须验证消费端编译兼容，不兼容时拆分或走生成方案；不预写未确认端的实现。
  - 旧裁决作废：domain 不再并入 api-contract——领域语义还服务端上预判、本地校验与测试，不止 HTTP 接口，独立成 domain-spec 单源（R-U12 的契约单源不因此受影响）。
- 落位：HLD·工程化落位。
- 违反信号：端型大项 monorepo 缺任一必建规格契约包；domain 语义塞进 api-contract 单点维护；预写未确认端的语言实现包；常规单仓为凑结构建空壳 packages/。

### R-U31 Token 纪律
- 规则：Design Token 保持一份权威规格，用 style-dictionary 或项目既有生成器派生各端产物；基础色阶可用色值级命名，组件消费语义 Token，平台差异走覆盖层。禁止手改生成物；生成物可按项目需要提交或在构建生成，CI 验证与规格一致。运行时换肤须单独声明实现与验收，不因 Token 生成而默认承诺支持。
- 落位：AGENTS.md·禁改目录；流水线·CI（生成 + diff 检查）。
- 违反信号：手改生成物；组件绕过语义 Token 且无平台例外；产物与权威规格漂移。

### R-U32 配置只住一层
- 规则：配置覆盖链按项目声明（示例：用户维度 > 配置中心 > 环境文件 > 代码默认值），每项指定主维护入口、适用覆盖层与回退值；代码默认值/故障兜底不算第二份权威配置，禁止无优先级的多源维护。客户端仅持公开配置/公开标识或受控短期凭据，长期敏感密钥留服务端。
- 落位：HLD·工程化落位；AGENTS.md。
- 违反信号：配置多源无主入口/优先级；远程配置无兜底；长期敏感密钥出现在客户端。

### R-U33 AGENTS.md 最小约束集
- 规则：项目 AGENTS.md 必须含：项目结构地图与依赖方向、统一命令、关键概念词典、分层规范与禁区、禁改目录（生成产物清单）、特殊端说明、验证要求（改 X 必须跑 Y）；配套机器可查边界（依赖 lint / 构建门禁 / 契约测试），AI 犯错让流水线红。
- 落位：工程资产·AGENTS.md（本库各端规则的宿主）。
- 违反信号：AI 改动无对应 lint/测试可拦截。

### R-U34 AI 错误四防线
- 规则：幻觉 API → 官方文档/目标 SDK 取证 + 编译与测试；文件越界 → diff 对照任务卡，依赖越界 → 分层 lint（两者不可互代）；语义偏离 → 契约与受影响端场景测试；大改失控 → 分域迁移与回归锁定。不以 AI 提效为由绕过范围授权、方案批准或回归验证。
- 落位：AGENTS.md；流水线·CI。
- 违反信号：无 API 证据；只用依赖 lint 声称文件边界已验证；未经授权大改或以提效为由弱化回归。

### R-U35 CI 全量门禁
- 规则：合入前 CI 覆盖全部适用检查，影响感知可缩小任务集但共享/全局影响必须扩展验证；CI 绿灯是必要条件，不替代项目人工审批。合入前检查与发布/提审/灰度分阶段，不能把 CI 自动等同部署授权；发布遵循工作流。iOS 原生构建/签名使用 macOS/Xcode，平台无关检查可在其他 runner；微信小程序可用 miniprogram-ci，其他小程序使用各自官方工具。
- 落位：流水线·CI。
- 违反信号："在我机器上是好的"作为合入依据；以 CI 绿灯为由绕过人工审批。

### R-U36 读写分离纪律
- 规则：读多写少先评估索引、查询和缓存收益，再依据瓶颈评估读副本；采用副本时声明延迟与一致性预算。需要 read-your-writes 的路径读主库或使用经过验证的会话/复制位点等待机制；允许最终一致的业务可明确读副本，不把所有写后读都强制读主库。
- 落位：HLD·数据设计。
- 违反信号：需要 read-your-writes 却无延迟/位点保障地读副本；未声明一致性预算。

### R-U37 Adapter 接口三路消费
- 规则：Adapter 接口保持规格单源，各端择可行路径消费：①兼容语言/工具链直接 import，构建时选择平台实现，UTS/ArkTS 与 TS 的兼容须验证 ②跨语言用明确描述方法、入参、返回值、异步与错误语义的接口规格生成，JSON Schema 可描述数据但不单独代表完整方法协议 ③无法生成则手写对齐签名/错误码，受影响端跑同一组契约场景。三种是消费路径，不是必须依次执行的批次。
- 落位：HLD·Adapter 接口设计；契约资产·接口规格；流水线·CI（受影响端契约测试）。
- 违反信号：各端手写互不对齐的接口定义；手写对齐路径无契约测试。

### R-U38 跨仓单源分发
- 规则：单源资产独立成仓（或由服务端仓承载）时，消费方只依赖版本化生成产物（私有包 registry，或构建时按 tag 锚定拉取生成），仓内禁出现单源拷贝；变更入口唯一——要改契约去单源仓提变更，发新版本后消费方升级锁定版本；消费方 CI 校验"产物与锁定版本一致"，升级依赖的变更必须引用单源仓 tag；禁依赖"最新"。
- 落位：AGENTS.md·禁改目录；流水线·CI（产物 diff + 版本引用检查）。
- 违反信号：仓内手改生成产物；依赖"最新"而非锁定版本；契约字段各仓各写。
